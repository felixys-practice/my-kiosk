# 환불 PG 데이터와 상태

## 영속 데이터 보존

스키마·마이그레이션을 변경하지 않는다.

| 대상 | 이번 작업의 처리 |
| --- | --- |
| Payment | 환불과 연결된 기존 결제를 사용한다. 승인 요청·상태·거래 ID 저장 방식은 변경하지 않는다. |
| Ticket | 기존 환불 확정에서 REVOKED로 변경하고 PG 실패 후에도 유지한다. 발급 방식은 변경하지 않는다. |
| Refund | 기존 확정 금액·지급 현황·금액 검토·별도 지급 예약을 유지한다. |
| PaymentCancel | 기존 요청 ID·금액·담당 토큰·리스·재전송 횟수·최종 결과·실제액을 유지한다. |
| 원장·멱등 기록 | 기존 고유 제약과 기록 순서를 유지한다. |

## 모의 취소 결과

`SimulatedPgClient`의 Map에 다음 정보를 보관한다.

- 키: `PaymentCancel.id`.
- 값: 최초 요청 금액, 모의 취소 거래 ID, 실제 모의 취소액, 성공 결과.
- 최초 요청은 요청액 전액의 취소 성공 결과를 생성한다.
- 같은 ID·금액 재요청은 같은 결과를 반환한다. 다른 금액의 재요청은 최초 기록을 유지하고 UNKNOWN으로 반환한다.
- 저장된 ID 조회는 최초 결과를 반환한다. 기록이 없으면 QUERY_ERROR다.
- 재시작·다른 프로세스와 메모리를 공유하지 않는다. 기록이 없다는 사실은 PG 미접수 확정이 아니다.

승인 결과 Map·자동 콜백 작업·타이머·새 DB·Redis 키는 추가하지 않는다.

## 입력과 결과

- 내부 요청은 기존 paymentCancelId·amount를 사용한다. 요청 금액은 0 이상 안전 정수여야 한다.
- 성공 결과의 거래 ID는 비어 있지 않아야 하며 실제액은 0 이상 안전 정수여야 한다.
- 요청액과 다른 실제 취소액도 실제 결과로 업무 서비스에 전달하여 기존 금액 검토 규칙을 적용한다.
- 실제 PG의 원승인 ID 등 추가 필수 정보는 실제 연동 시 계약을 검토한다. 현재 최소 계약이 실연동에 충분하다고 주장하지 않는다.

## 상태 변경 주체

PG 계층은 모의 Map 외의 업무 DB를 읽거나 쓰지 않는다. 실제액·취소 성공·지급 상태·원장은 기존 RefundResultService가 트랜잭션에서 반영한다. 전송·조회 담당과 재전송 조건은 기존 환불 서비스에 남긴다.

자세한 결과별 상태는 [기존 계약 §8](../002-refund-completion/contracts/rest-api.md)을 유지한다. 결제 승인 데이터 설계는 [별도 인계](payment-handoff.md) 대상이다.
