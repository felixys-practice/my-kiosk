# 환불 PG 구조 설계 결정

**상태**: 2026-11-14 결제 승인 작업 분리 반영. 설계 기록이며 구현·테스트 통과 기록이 아니다.

## R1. PgService와 PgClient의 책임 분리

**결정**: 환불은 PgService를 호출하고 서비스는 PG_CLIENT로 주입한 PgClient를 호출한다. RefundPgGateway·기존 취소 클라이언트 토큰을 제거한다.

**근거**: PgService에는 이미 제한 시간·통신 오류 처리 책임이 있다. 공통 호출 제어는 유지하고 PG사별 요청·응답 해석만 클라이언트에 둔다.

**대안**: 직접 PgClient 호출은 공통 호출 정책의 위치를 다시 나눠야 한다. 환불 Gateway 유지도 가능하지만 현재 동일 기능을 별도 토큰으로 유지할 필요가 부족하다. 테스트 대역 교체 목적만으로 기존 구조를 고정하지 않는다.

## R2. 가상 HTTP 응답 계약 제거

**결정**: PgClient는 기존 PgCancelSendResult·PgCancelQueryResult 의미를 표현하는 결과를 반환한다. 서비스는 제한 시간·예외·필수 결과 정보를 검증한다. PgRawResponse는 실제 운영 규격으로 유지하지 않는다.

**근거**: 변경 전 기준 커밋 `8fde6fc`의 pg-cancel.client.ts가 응답 형식을 가상이라고 명시한다. 이 파일은 003 구조 전환 후 제거한다. PG사 고유 코드를 PgService가 알면 통신 구현을 교체할 때 공통 서비스까지 바꿔야 한다.

**대안**: 가상 HTTP 형태 유지 또는 각 구현에 공통 timeout 중복 구현은 채택하지 않는다.

## R3. 결제 승인은 별도 브랜치로 분리

**결정**: 승인 요청·모의 승인·자동 승인 콜백·저장 완료 통지·저장 메서드 명칭 변경·승인 timeout 설정을 이번 범위에서 제외한다. 기존 requestVan·승인 콜백 업무는 유지한다. PgClient에는 취소·조회만 정의한다.

**근거**: 사용자가 결제 로직을 별도 브랜치에서 진행한다. 기존 콜백 중심 흐름을 모든 운영 PG의 승인 계약으로 고정할 근거가 없으며, 승인 API 응답에서 성공을 확인하는 방식도 검토해야 한다.

**대안**: 승인 메서드·비동기 모의 전달 골격까지 미리 작성하면 별도 결제 설계를 불필요하게 제한한다. 미래 확장을 위해 빈 메서드를 추가하지 않는다.

이전 논의·사용자 선택·코드 근거는 [payment-handoff.md](payment-handoff.md)에 보존했다. 기존 R3의 저장 완료 통지·R4의 자동 HTTP 콜백·R7의 승인 오류 설계는 현재 환불 계획에 적용하지 않는다. 승인액 불일치·좌석 실패의 시스템 환불은 기존 코드에서 새 취소 경로로 이어지도록 보존한다.

## R4. 모의 즉시 성공과 메모리 수명

**결정**: 취소는 즉시 요청액 전액 성공으로 반환하고 PaymentCancel.id별 Map에 저장한다. 같은 ID·금액은 같은 거래 ID·실제액을 반환한다. 다른 금액이면 새 성공 없이 UNKNOWN을 반환하고 최초 결과는 보존한다. 조회는 최초 결과를 반환한다.

기록 부재는 QUERY_ERROR다. 재시작·다른 프로세스에서도 확정 미접수로 바꾸지 않는다. 업무 DB를 모의 결과 저장소로 사용하지 않는다.

**근거**: 사용자 선택은 메모리 보관·즉시 취소 성공이다. 결과 불명·조회 실패·명시적 미접수 등은 기존 테스트 대역으로 검증할 수 있다.

**대안**: 외부 저장소·모의 PG 별도 서버·지연 성공 모드는 이번 기본 흐름 확인에 필요하지 않다.

## R5. 운영용 골격과 시작 검증

**결정**: PG_MODE=simulated 또는 production을 필수로 지정한다. 기본값은 없다. simulated는 development·test에만 허용한다. production은 구현의 validateConfiguration으로 준비 상태를 검사하며 현재 골격은 미구현 사유로 시작을 거부한다.

Joi에서 모드·환경을 검사하고 PgModule provider factory에서 구현 준비·필수 설정을 검사한다. 성공 시 모드·클래스명, 실패 시 사유·코드·항목명만 안내한다. 비밀값·전체 설정·응답 원문을 출력하지 않는다.

**근거**: 사용자 합의는 사용할 구현·설정이 없는 서버의 시작 거부와 운영용 템플릿 클래스의 실제 존재다. 클래스 존재를 실연동 준비 완료로 간주하지 않는다.

**대안**: 미연동 fallback·환경변수로 준비 완료 우회·가상 운영 키 요구는 채택하지 않는다. 실제 PG 설정 항목은 선정 후 정한다.

## R6. 계약과 테스트 보존

**결정**: PG 요청 이름은 requestPaymentCancel, 조회 이름은 inquirePaymentCancel로 통일한다. 취소 즉시 성공·비동기 콜백·조회 결과는 기존 결과 서비스에 모은다. 외부 API·상태·담당·재전송·원장 제약을 변경하지 않는다.

PgService 테스트는 PG_CLIENT를, 환불 E2E는 PgService를 대역으로 교체한다. 모의 취소·조회 연결은 실제 모의 구현으로 별도 검증한다. 시작 거부는 헌법 v1.6.0에 따라 실제 앱 시작을 검증한다.

**근거**: 현행 RefundDispatchService는 즉시 SUCCEEDED를 RefundResultService로 넘긴다. 기존 테스트에는 결과 분류·복구·동시성·부트스트랩 검증이 있으므로 업무 기대값과 구형 클래스 연결 검증을 구분해 옮겨야 한다.

**대안**: 기존 클래스 연결을 고정하거나 모의 구현만으로 실패·복구 검증을 대체하지 않는다.

## 기존 002 결정과의 차이

- E2E에서만 테스트 PG를 주입하던 제한에 개발 환경의 명시적 모의 취소·조회를 허용한다. 운영 모의 성공 금지는 유지한다.
- 미연동 구현으로 서버를 시작하던 동작은 시작 거부로 바꾼다. NOT_SENT의 업무 결과 의미는 보존한다.
- 실제 PG 통신은 여전히 범위 밖이다. 연구·계약 문서는 가상의 운영 규격을 확정하지 않는다.
