# Feature Specification: 환불 PG 호출 구조 정리와 구현 분리

**Feature Branch**: `feature/pg-client`
**Created**: 2026-11-14
**Status**: Draft — 결제 승인 작업 분리 반영

**Input**: 환불의 PG 결제 취소 요청·취소 결과 조회를 `PgService → PgClient`로 정리한다. 운영용 `ProductionPgClient` 골격과 개발용 `SimulatedPgClient`를 분리하고 환경별 선택·시작 검증을 제공한다. 결제 승인 연동은 별도 브랜치에서 진행한다.

## 구조 변경의 목적과 범위

### 변경 전 구조와 문제 (003 작업 시작 시점)

아래는 브랜치 생성 기준인 `8fde6fc`의 구조다. 현재 구현·검증 결과는 [검증 기록](verification.md)을 따른다.

```text
환불 전송·복구·재시도 서비스 → RefundPgGateway → PgService → PgCancelClient
```

- `RefundPgGateway`는 인터페이스와 DI 토큰이며 기본 구현은 `PgService`다. `PgService`는 제한 시간과 가상 HTTP 응답의 결과 분류를 담당한다.
- `PgCancelClient`는 취소 통신 인터페이스이며 기본 구현은 `UnconfiguredPgCancelClient`다. 미연동 구성에서도 서버가 시작되고 실제 취소는 전송 전 실패로 처리된다.
- 실제 PG사별 응답 해석과 공통 호출 제어를 분리하고, 운영용 골격·개발용 모의 구현을 같은 인터페이스로 선택할 수 있게 한다.
- 결제 승인 요청은 현재 내부 `requestVan()`을 사용한다. 이번 작업에서 이 경로와 승인 콜백 업무 로직은 변경하지 않는다.

### 목표 구조와 책임

```text
환불 전송·복구·재시도 서비스 → PgService → PgClient
                                           ├ SimulatedPgClient
                                           └ ProductionPgClient(실제 연동 미구현 골격)
```

| 구성 | 책임 |
| --- | --- |
| 환불 업무 서비스 | 환불 확정·상태 변경·실제 지급액·원장 반영, 업무상 조회·재전송·복구 조건 판단 |
| `PgService` | 취소 요청·조회 호출의 제한 시간·중단·통신 오류·필수 결과 정보 검증 |
| `PgClient` | 취소 요청·취소 결과 조회의 공통 인터페이스. 승인 메서드는 이번에 정의하지 않음 |
| `ProductionPgClient` | 실제 PG 요청·인증·통신·응답 해석을 추가할 운영용 골격. 미구현 상태에서는 시작 거부 |
| `SimulatedPgClient` | 실제 외부 거래 없이 취소 즉시 성공과 저장된 취소 결과 조회 제공 |

기존 `PgRawResponse`는 가상 형식이므로 운영 규격으로 고정하지 않는다. 업무 서비스는 클라이언트 구현을 직접 선택하지 않으며, PG 계층은 업무 DB를 변경하지 않는다.

### 포함·제외 범위

| 구분 | 범위 |
| --- | --- |
| 구조 변경 | `RefundPgGateway`·`REFUND_PG_GATEWAY` 제거, `PgCancelClient`·`PG_CANCEL_CLIENT`를 `PgClient`·새 주입 토큰으로 대체, 관련 호출처·DI·테스트 정리 |
| 새 동작 | 개발용 모의 취소·조회, 환경별 구현 선택, 잘못된 구성의 서버 시작 거부 |
| 운영 연동 준비 | 운영용 클래스의 취소 요청·조회 메서드 골격과 실제 연동 지점 설명 |
| 별도 결제 브랜치 | 승인 요청·응답·조회·복구 설계, 모의 승인·자동 승인 콜백, 승인 저장 메서드 명칭 변경 |
| 제외 | 실제 PG 통신, 새 결제수단, 환불 정책 개편, 새로운 외부 저장소 |

`requestVan()` 교체, `requestedPayment()` 명칭 변경, `notifyApprovalRequestStored()`와 승인 전용 설정은 이번에 구현하지 않는다. 승인 인터페이스를 미리 고정하지 않고 [결제 인계 문서](payment-handoff.md)를 별도 작업의 출발점으로 사용한다.

### 산출물 역할

- `plan.md`: 메서드·DI·변경 순서·테스트 대역·기존 문서 갱신 대상.
- `contracts/pg-client.md`: 취소 요청·조회와 환경 선택·시작 검증 계약.

## Clarifications

### Session 2026-11-14

- Q: 모의 거래 결과를 서버 재시작 후에도 유지할까요? → A: 메모리에만 보관하고 재시작 시 초기화한다. 기록이 없는 취소 요청 조회는 `QUERY_ERROR`다.
- Q: 모의 취소 요청은 즉시 성공을 반환할까요? → A: 즉시 성공을 반환하고 이후 조회에서도 같은 결과를 반환한다.
- 범위 변경: 결제 로직은 별도 브랜치에서 진행한다. 기존 모의 승인 자동 콜백·승인 예외 처리 논의는 payment-handoff.md로 인계했으며 이번 요구사항이 아니다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 환불 PG 구조 변경과 기존 업무 보존 (Priority: P1)

개발자는 환불의 취소 요청·결과 조회에 같은 서비스·클라이언트 구성을 적용한다. 고객·점주·운영자는 기존 환불 동의·금액·권한·복구 규칙을 그대로 적용받는다.

**Why this priority**: 구조를 바꾸면서 이용 종료·실제 지급액·중복 방지 규칙이 달라지면 안 된다.

**Independent Test**: 호출 관계와 책임을 정적 검토하고, 테스트 대역으로 기존 환불 HTTP 시나리오의 상태·실제액·원장·호출 횟수·동시성·복구를 확인한다.

**Acceptance Scenarios**:

1. **Given** 고객이 환불 가능한 미사용 이용권을 보유하고 테스트 대역이 취소 요청의 전송 전 실패를 반환하는 경우, **When** 고객이 환불을 신청하면, **Then** `Ticket.status=REVOKED`, `Refund.decisionStatus=ACCEPTED`, `Refund.payoutStatus=ACTION_REQUIRED`, `PaymentCancel.status=FAILED`, `PaymentCancel.failureCode=SEND_FAILED`로 처리하고 실제 지급액·원장을 늘리지 않는다.
2. **Given** 전송 후 결과 불명인 PG 결제 취소 요청, **When** 복구 조회가 미접수를 확정하면, **Then** 기존 조건·한도에 따라 같은 `PaymentCancel.id`·금액으로 재전송하며 새 환불을 만들지 않는다.
3. **Given** 같은 PG 결제 취소 요청의 성공 결과, **When** 콜백·조회·즉시 응답이 중복 도착하면, **Then** 실제 지급액과 원장을 중복 반영하지 않는다.
4. **Given** 기존 결제 승인 콜백에서 승인액 불일치가 확인된 경우, **When** 시스템 환불을 시작하면, **Then** 기존 금액·트랜잭션·이용권 미발급 규칙을 유지하고 커밋 후 새 PG 호출 구조로 취소를 요청한다.
5. **Given** 기존 결제 승인 처리에서 좌석 배정을 확정하지 못한 경우, **When** 시스템 환불을 시작하면, **Then** 기존 대상·이용 종료·배정 해제 규칙을 유지하고 커밋 후 새 PG 호출 구조로 취소를 요청한다.

4·5항은 기존 결제 업무를 변경하는 요구가 아니라 환불 호출 경로 변경의 회귀 검증이다.

### User Story 2 - 개발 환경에서 모의 취소·조회 확인 (Priority: P1)

개발자는 실제 승인 완료 데이터 또는 기존 시나리오 시드로 환불 대상을 준비하고, 모의 PG로 취소 성공·환불 반영을 확인한다.

**Why this priority**: 실제 외부 거래 없이 환불 성공 흐름을 확인할 수 있어야 한다.

**Independent Test**: 개발용 구현을 선택하고 환불 HTTP API를 실행한다. 모의 결과 조회와 메모리 수명도 앱을 통해 생성한 요청을 기준으로 검증한다.

**Acceptance Scenarios**:

1. **Given** 개발용 모의 PG를 선택하고 환불 가능한 이용권이 준비된 경우, **When** 환불을 신청하면, **Then** 요청액 전액의 취소 성공·모의 취소 거래 ID를 즉시 반환하고 기존 환불 서비스가 지급 상태·실제액·원장을 반영한다. 외부 금전 거래는 발생하지 않는다.
2. **Given** 모의 PG에 취소 결과가 저장된 요청, **When** 해당 요청을 조회하면, **Then** 저장된 취소 거래 ID와 금액을 반환한다.
3. **Given** 모의 PG에 결과가 저장된 요청, **When** 서버 재시작 후 같은 요청을 조회하면, **Then** `QUERY_ERROR`를 반환한다.
4. **Given** 모의 PG에 기록이 없는 요청, **When** 해당 요청을 조회하면, **Then** `QUERY_ERROR`를 반환하고 미접수 확정에 따른 재전송을 하지 않는다.

### User Story 3 - 환경 선택과 서버 시작 검증 (Priority: P1)

개발자·운영 담당자는 선택된 구현을 시작 로그로 확인하고 사용할 수 없는 구성의 시작을 거부한다.

**Why this priority**: 모의 거래를 운영 거래로 처리하거나 미구현 클래스를 실제 연결로 오해하면 안 된다.

**Independent Test**: 허용 구성은 서버 시작과 HTTP 동작을 확인한다. 시작 거부 구성은 헌법 v1.6.0에 따라 실제 서버 시작 시도·거부 사유·시작 실패를 검증한다.

**Acceptance Scenarios**:

1. **Given** 개발 환경, **When** 모의 PG를 명시적으로 선택하여 시작하면, **Then** 서버가 시작되고 시작 로그에 모드·구현 클래스명을 표시한다.
2. **Given** 운영 환경, **When** 모의 PG를 선택하여 시작하면, **Then** 환경에서 허용되지 않는다는 사유를 알리고 시작을 거부한다.
3. **Given** 모드가 없거나 지원하지 않는 값인 경우, **When** 시작을 시도하면, **Then** 설정 오류 사유를 알리고 시작을 거부한다.
4. **Given** 운영용 클래스가 골격 상태인 경우, **When** 해당 구현으로 시작을 시도하면, **Then** 실제 PG 통신 미구현 사유를 알리고 시작을 거부한다.
5. **Given** 선택한 구현의 필수 설정이 누락된 경우, **When** 시작을 시도하면, **Then** 비밀값 없이 항목명을 안내하고 시작을 거부한다. 실제 PG사의 항목은 선정 후 정한다.

### Edge Cases

- 취소 요청의 타임아웃·일반 통신 예외는 `UNKNOWN`, 조회의 타임아웃·예외는 `QUERY_ERROR`다.
- 일반 HTTP 404·인증 오류·조회 반영 지연·메모리 기록 부재는 확정 미접수가 아니다.
- 취소 성공의 실제액·거래 ID가 없거나 유효하지 않으면 성공 근거로 쓰지 않는다.
- 반복 콜백·즉시 응답·조회는 기존 최종 결과 보호·실제 지급액·원장 규칙을 유지한다.
- 기존 미확정 요청 재전송·확정 실패 후 새 요청·별도 지급 예약 조건을 유지한다.
- 모의 구현은 여러 서버 간 메모리 공유와 재시작 복구를 보장하지 않는다.

## Requirements *(mandatory)*

### Structural Requirements

- **SR-001**: 환불 전송·복구·재시도의 취소 요청·조회는 `PgService → PgClient`를 거쳐야 한다. 업무 서비스에서 특정 구현을 선택하지 않는다.
- **SR-002**: PG사별 요청·응답 해석은 `PgClient` 구현, 공통 제한 시간·통신 오류·필수 결과 정보 검증은 `PgService`가 담당한다. 같은 처리를 중복 구현하지 않는다.
- **SR-003**: 업무 상태·실제 지급액·원장·재전송·복구 정책은 기존 업무 서비스에 유지한다. PG 계층은 업무 DB를 변경하거나 업무 서비스를 호출하지 않는다.
- **SR-004**: `PgCancelClient`·`PG_CANCEL_CLIENT`·`UnconfiguredPgCancelClient`를 제거하고 `PgClient`·새 주입 토큰·운영용 골격·개발용 구현으로 대체한다. 별도 미연동 기본 구현은 두지 않는다. 결제 승인 메서드는 이번 계약에 추가하지 않는다.
- **SR-005**: `RefundPgGateway`·`REFUND_PG_GATEWAY`를 제거하고 호출처·DI·테스트 대역을 전환한다. 기존 업무·동시성·복구 기대값을 약화하지 않는다.
- **SR-006**: 테스트별로 `PgService`·`PgClient` 중 교체할 객체를 계획에 명시하고 실제 모의 구현 연결도 검증한다.
- **SR-007**: 기존 002의 기술 설계와 다른 부분은 문서에 반영하되 과거 테스트·작업 기록을 다시 쓰지 않는다.

### Functional Requirements

- **FR-001**: PG 결제 취소 요청·취소 결과 조회를 제공한다. 결제 승인 요청·콜백 처리·승인 복구는 이번에 변경하지 않는다.
- **FR-002**: 기존 환불 공개 요청·응답·인증·인가·동의·금액·멱등성·동시성·복구 규칙을 보존한다.
- **FR-003**: 취소 결과는 기존 업무 서비스에 전달하고 PG 계층에서 지급 상태·이용권·원장을 변경하지 않는다.
- **FR-004**: 취소 요청 결과 `NOT_SENT / ACCEPTED / UNKNOWN / SUCCEEDED / REJECTED`와 조회 결과 `SUCCEEDED / FAILED / IN_PROGRESS / NOT_FOUND / QUERY_ERROR`의 의미를 유지한다.
- **FR-005**: 환불 확정 커밋 후 PG 취소를 요청하고, 실패하더라도 확정된 이용 종료·환불 금액을 되돌리지 않는다.
- **FR-006**: 기존 요청 ID·금액·리스·담당 토큰·카운터·별도 지급 예약의 상호 배제·최종 결과 보호를 유지한다.
- **FR-007**: 기존 승인액 불일치·좌석 배정 실패의 시스템 환불과 기존 승인·취소 콜백 서명·본문·수신 확인·저장 실패 응답을 보존한다. 모의 승인이나 자동 승인 콜백은 추가하지 않는다.
- **FR-008**: `SimulatedPgClient`는 요청액 전액의 취소 성공과 모의 취소 거래 ID를 즉시 반환하고 같은 요청 조회에 같은 결과를 반환한다. 모의 구현은 명시적으로 선택하고 운영 환경에서는 거부한다.
- **FR-010**: 시작 시 모드·구현 준비·환경 허용·필수 설정을 검사한다. 누락·미지원 모드·미구현·설정 누락·운영 모의 선택은 사유를 알리고 시작을 거부한다. 성공 시 모드·클래스명을 로그에 남긴다. 자동 모의 대체와 비밀값·개인정보 원문 노출을 금지한다. 실제 PG 접속은 검사하지 않는다.
- **FR-011**: `ProductionPgClient` 골격에 취소 요청·조회 메서드와 요청 매핑·인증·통신·중단·응답 해석·전송 확실성 판단의 연동 지점을 설명한다. 미구현 메서드는 오류를 내며 성공·접수·확정 미접수를 꾸며 반환하지 않는다. 실제 PG 통신·규격은 만들지 않는다.
- **FR-012**: 기존 환불 E2E·PG 계층 테스트를 새 교체 지점에 맞추고 결과별 상태·실제액·원장·호출 횟수 검증을 유지한다.
- **FR-014**: 모의 취소 결과는 프로세스 메모리에만 보관하고 재시작 시 초기화한다. 외부 저장소를 추가하지 않으며 기록이 없는 조회는 `QUERY_ERROR`다.

FR-009는 FR-010에 통합했고, FR-013(모의 승인 자동 전달)은 별도 결제 작업으로 이관했다. 나머지 ID는 기존 참조를 위해 유지한다.

### Key Entities

#### Payment

- **정의**: 주문의 결제 요청·승인 결과 기록.
- **이번 범위**: 기존 환불 대상과 연결된 결제 기록을 사용한다. 승인 상태 전이·요청 메서드는 변경하지 않는다.

#### Ticket

- **정의**: 고객이 구매한 상품을 이용할 수 있는 권리를 나타내는 이용권.
- **환불 시 처리**: 환불 확정 트랜잭션에서 `Ticket.status=REVOKED`로 변경하고 PG 취소 실패 후에도 유지한다. 발급 로직은 변경하지 않는다.

#### Refund

- **정의**: 확정된 환불 금액·지급 현황 기록.
- **보존 규칙**: `Refund.decisionStatus`·`Refund.payoutStatus`·확정액 불변 규칙을 유지한다.

#### PaymentCancel

- **정의**: 개별 PG 결제 취소 시도 기록.
- **식별자**: `PaymentCancel.id`는 PG 멱등 키이며 `Refund.id`·클라이언트 요청 키·PG 취소 거래 ID와 구분한다.

#### 모의 취소 결과

- **정의**: 개발용 PG가 조회에 반환할 취소 결과.
- **관리**: 업무 DB와 구분해 메모리에 보관하며 재시작 후 기록이 없으면 `QUERY_ERROR`다.

## Success Criteria *(mandatory)*

### 구조 변경 완료 기준

- **SC-006**: 모든 환불 취소 요청·조회 호출처가 SR-001을 따르고 구형 인터페이스·토큰·미연동 클래스가 남지 않는다. 승인 경로의 `requestVan()`은 이번 제거 대상이 아니다.
- **SC-007**: PG 응답 해석·공통 호출 제어·업무 DB 변경을 각 담당 계층에서 수행한다. 중복 처리와 PG 계층의 업무 서비스 호출이 없어야 한다. 코드·테스트 근거를 기록한다.
- **SC-008**: DI·테스트 교체·관련 002 설계 문서의 갱신 대상을 식별하고 각 대상의 정리·유지 근거를 확인한다.
- **SC-009**: 운영용 골격·개발용 구현이 같은 취소·조회 계약을 구현한다. 가상의 PG 규격을 운영 규격처럼 제공하지 않는다.

### 동작 검증 기준

- **SC-001**: 기존 환불·시스템 환불 회귀 시나리오의 상태·금액·원장·복구 결과가 기존 계약과 일치한다.
- **SC-002**: 준비된 미사용 이용권의 환불부터 모의 취소 성공·조회·원장 반영까지 확인하고 외부 금전 거래는 0건이다.
- **SC-003**: FR-010의 거부 구성은 사유 안내 후 시작을 거부하고 개발·테스트 환경의 명시적 모의 선택은 시작한다.
- **SC-004**: 같은 PG 취소 요청의 성공 결과를 중복 수신해도 실제 지급액·원장을 중복 반영하지 않는다. 기존 승인 콜백의 중복 발급 방지도 회귀 검증한다.
- **SC-005**: 전송 전 실패는 `PaymentCancel.status=FAILED`·`Refund.payoutStatus=ACTION_REQUIRED`로 처리하고 자동 조회에서 제외한다. 결과 불명은 조회로 확인하며 조회 오류는 기존 복구 규칙을 따른다. 성공 확인 전에 실제 지급액·원장을 반영하지 않는다.

## Assumptions

- 실제 PG는 미정이다. 운영용 골격을 선택하면 시작을 거부하며 개발 환경은 모의 구현을 사용한다.
- 기존 `scripts/dev-scenario.ts`와 `refund-unused`를 환불 대상 준비에 사용할 수 있다. 이 도구는 승인 성공 데이터를 직접 생성하며 승인 흐름을 검증하지 않는다. 이번에는 수정하지 않는다.
- 실패·지연·결과 불명은 기존 테스트 대역으로 검증한다. 모의 구현에 장애 선택 기능·외부 저장소·다중 PG 라우팅을 추가하지 않는다.
- 기존 002 업무 기준은 [spec](../002-refund-completion/spec.md)과 [API §7·§8](../002-refund-completion/contracts/rest-api.md)이다. E2E 전용 대역 제한에 개발용 모의 취소·조회를 허용하는 설계 변경과 시작 검증을 별도 문서에 반영한다. 운영 모의 성공 금지는 유지한다.
- 코드·DB·기존 002 문서의 실제 수정은 후속 구현 승인 범위다. 단계별 승인, feature/pg-client 유지, 기존 미추적 .serena/·src/idempotency-challenge/ 보존, 별도 커밋·푸시·PR 요청 조건을 유지한다.
