# Phase 0 조사: 좌석 타입(고정석·자유석) 추가

기술 맥락에 NEEDS CLARIFICATION은 없다. 아래는 spec을 현재 코드에 적용할 때 정해야 하는 설계 결정이다.
**[사용자 확인 필요]** 표시는 헌법 원칙 IV(축약·생략 시 사용자 확인)에 해당해 확인을 받아야 하는 항목이다.

## R1. 고정석 지정을 어디에 저장하는가

- **결정**: 새 테이블 `SeatAssignment`(좌석 지정)에 저장한다. 한 행이 "좌석 1개 ↔ 이용권(또는 주문 항목) 1개"의 지정 1건이다.
  상태는 `HELD`(주문 선점) → `ACTIVE`(이용권 확정) → `RELEASED`(해제)로 전이한다.
  좌석당 유효 지정 1개는 `UNIQUE (seat_id) WHERE status IN ('HELD','ACTIVE')` 부분 유일 인덱스로 보장한다.
- **근거**: 이용권 발급(결제 성공) 전에 좌석을 선점해야 하고(R2), 해제·재지정 이력이 남아야 한다.
  기존 프로젝트도 `UsageSession`, `TicketPause`에서 같은 부분 유일 인덱스 방식으로 "활성 1개"를 보장한다.
- **검토한 대안**: `Ticket.assignedSeatId` 컬럼 — 이용권이 생기기 전(주문 단계) 선점을 표현할 수 없고 해제 이력이 사라져 기각.

## R2. 고정석 좌석을 언제 선점하는가 **[사용자 확인 완료]**

- **결정**: 주문 생성(`POST /orders`) 시 `HELD`로 선점하고, 결제 성공 시 발급된 이용권에 연결해 `ACTIVE`로 확정한다.
  선점이 풀리는 경우는 세 가지다.
  - 이용자가 뒤로 가기·취소: 키오스크가 주문 취소 API(`PATCH /orders/:orderId/cancel`, 신규)를 호출해 **즉시** 해제(`ORDER_CANCELLED`).
  - 결제 실패: 결제 콜백에서 즉시 해제(`PAYMENT_FAILED`).
  - 방치: 키오스크가 꺼지는 등 취소 호출이 오지 않으면 **선점 유효시간 10분**(환경 변수로 설정)이 지난 뒤 풀린다(`HOLD_EXPIRED`).
    10분은 취소 호출이 없을 때를 대비한 안전장치다.
- **사용자 확인**: 2026-10-21 승인. 취소 시 즉시 해제, 방치 시 10분.
- **근거**: 좌석 예약 업계의 일반적인 방식(장바구니·결제 단계의 임시 선점 + 유효시간)이다.
  결제 성공 시점에만 검사하면, 같은 좌석을 두 명이 결제했을 때 PG 승인이 끝난 뒤 충돌을 발견해 승인 취소(환불)를 해야 한다.
- **spec 반영**: 동시 구매 기준은 "먼저 좌석을 선점(주문)한 한 건만 성공"이다. spec 경계 상황도 analyze 단계에서 이 기준으로 정정했다.
- **검토한 대안**: 결제 성공 시점 검사 + 충돌 시 PG 승인 취소 — 환불 흐름까지 엮여 복잡하고 이용자 경험이 나빠 기각.
- **현재 코드 사실**: 주문 취소 API와 주문 상태 필드가 없다. 주문 취소 API는 "결제 성공 전인 주문의 선점 해제"만 하고,
  결제(`Payment`)가 SUCCESS인 주문이면 거부한다(환불은 기존 환불 흐름).

## R3. 만료된 이용권의 지정을 언제 해제하는가 **[사용자 확인 완료]**

- **현재 코드 사실**: 이용권이 `EXPIRED`로 바뀌는 코드가 없다. 기간권 만료(`expiresAt`), 시간권 소진 기한(`minuteExpireDeadline`),
  기간권 활성화 기한(`activationDeadline`)은 시간이 지나면 의미상 만료되지만 상태 전이 이벤트가 없다.
- **결정**:
  - 이벤트가 있는 종료는 같은 트랜잭션에서 즉시 해제한다: 시간권 소진(`SessionLifecycleService.endSession`의 EXHAUSTED 전이),
    환불 확정(`RefundService`가 `confirmRefundSuccess`를 호출하는 트랜잭션의 REVOKED 전이), 일시정지(`TicketPauseService.pauseTicket`).
  - 시간 경과형 만료는 **지연 해제**한다. 좌석 선점·재지정·이동 시 대상 좌석의 기존 `ACTIVE` 지정을 조회해,
    연결된 이용권이 기한을 넘겼으면 같은 트랜잭션에서 `RELEASED`(사유 `TICKET_EXPIRED`)로 바꾼 뒤 진행한다.
    좌석 조회 API도 같은 판정으로 "선택 가능" 여부를 계산한다.
- **근거**: FR-017의 "즉시 해제"를 이용자가 관찰할 수 있는 결과(만료 직후 다른 이용자가 그 좌석을 선택할 수 있음)로 충족한다.
  만료 배치를 새로 만드는 것은 "이용권 만료 처리"라는 별도 기능이라 이번 범위(헌법 원칙 V)를 넘는다.
- **검토한 대안**: BullMQ 만료 Job 또는 주기 배치로 `EXPIRED` 전이와 해제를 함께 처리 — 범위 밖이라 기각.
- **빈 좌석 표시 방법**: 좌석 조회 API는 저장된 상태값(`HELD`/`ACTIVE`)을 그대로 쓰지 않고, 조회 시점(`now`)에
  "유효한 지정"인지 다시 계산해 `isAssignable`을 내려준다(data-model.md "유효한 지정 판정").
  그래서 DB 행이 아직 `RELEASED`가 아니어도 만료 시각이 지난 순간부터 화면에는 빈 좌석으로 보인다.
  이용자가 그 좌석을 고르면 선점 트랜잭션에서 행을 `RELEASED`로 바꾼 뒤 새 선점을 만든다.
- **이 방식의 주의점**: 지정 여부를 판단하는 모든 곳이 같은 판정 함수를 써야 한다. 판정은 `SeatAssignmentService` 계층의 순수 함수(`seat-assignment.policy.ts`) 한 곳에 둔다(헌법 원칙 I).
- **사용자 확인**: 2026-10-21 지연 해제 사용. 이용권 만료 처리 기능은 만들지 않는다.
- **FR-017 해석**: FR-017의 "즉시"는 DB 상태 전이가 아니라 관찰 가능한 결과(만료 즉시 다른 이용자가 선택 가능) 기준이다.

## R4. 고정석 상품의 주문 수량 **[사용자 확인 완료]**

- **현재 코드 사실**: 주문 항목은 `{ productId, quantity }`이고, 수량만큼 주문 항목(이용권)이 생긴다.
- **결정**: 고정석 상품은 주문 항목 1개에 좌석 1개를 지정한다. 고정석 상품 줄은 `quantity`가 1이어야 하고 `seatId`가 필수다.
  같은 고정석 상품을 2장 사려면 좌석을 달리해 줄을 2개 보낸다.
- **근거**: FR-007은 "고정석 좌석 하나의 선택이 필수"다. 수량 2에 좌석 1개는 의미가 맞지 않는다.
- **검토한 대안**: `seatIds: string[]`(길이 = 수량) — DTO 검증이 복잡해지고 같은 결과를 줄 단위로 표현할 수 있어 기각.
- **사용자 확인**: 2026-10-21 "모든 이용권은 좌석 1개만 소유할 수 있다". 이용권당 ACTIVE 지정 1개는
  `UNIQUE (ticket_id) WHERE status = 'ACTIVE'`로 보장한다(data-model.md).

## R5. 고정석 → 고정석 이동 중 이용 상태 유지 (FR-015b)

- **결정**: 이용 중이면 활성 `UsageSession`의 `seatId`를 새 좌석으로 바꾼다. `startedAt`, `plannedEndAt`, BullMQ Job은 그대로 둔다.
  같은 트랜잭션에서 기존 지정 `RELEASED`(사유 `SEAT_MOVED`), 새 지정 `ACTIVE`를 만든다.
- **근거**: 세션을 끝내고 새로 만들면 시간권 잔여시간이 차감되고 퇴실·입실 기록이 생겨 "이용 중 상태 유지"와 어긋난다.
- **검토한 대안**: 세션 종료 후 재생성 — FR-015b와 충돌해 기각.

## R6. 좌석 타입 변경 중 즉시 퇴실 (FR-019)

- **결정**: `TicketPauseService.pauseTicket`과 같은 패턴을 쓴다. 트랜잭션 안에서 `SessionLifecycleService.endSession`으로 세션을 끝내고
  (시간권은 사용 시간 차감), 커밋 후 BullMQ 자동 종료 Job을 제거한다. 자동 입실은 하지 않는다.
- **근거**: 세션 종료 로직의 유일한 원천(`SessionLifecycleService`)을 재사용해 시간 차감 규칙을 한 곳에서 유지한다.

## R7. 변경 이력 저장 방식 (FR-020, FR-021)

- **결정**: 새 테이블 `TicketSeatChange`에 변경 1건당 1행으로 저장한다(변경 종류, 전후 타입, 전후 좌석, 사유, 변경자, 시각).
- **근거**: 기록할 항목이 고정돼 있어 행 단위가 조회·검증에 단순하다.
- **검토한 대안**: `ProductHistory`처럼 필드 단위(필드명·이전값·이후값) — 범용적이지만 이 기능에서는 조회가 복잡해져 기각.

## R8. API가 없는 요구사항 **[사용자 확인 완료]**

- **현재 코드 사실**:
  - 상품은 등록·조회 API만 있고 **수정 API가 없다**(`ProductController`: POST, GET). 변경 이력 모델 `ProductHistory`는 있다.
  - 좌석 수정 DTO(`UpdateSeatDto`)는 이름·번호만 받고, **좌석 상태(이용 가능/이용 불가)를 바꾸는 API가 없다**.
- **결정** (2026-10-21 사용자 승인: 두 API를 함께 만든다):
  - 상품 수정 API `PATCH /shops/:shopId/products/:productId`를 만든다. 수정 시 바뀐 필드마다 `ProductHistory`에 기록한다
    (한 번의 수정은 같은 `changeGroupId`). 기존 주문은 `OrderItem` 스냅샷이므로 영향이 없다.
  - 좌석 수정 API(`PATCH /seats/:seatId`)에 `status`(이용 가능/이용 불가)를 추가하고 FR-022 가드를 적용한다.
- **정정**: clarify 질문 5에서 "좌석은 지금도 점주가 이용 불가로 바꿀 수 있다"고 설명했으나, 코드 확인 결과 그런 API는 없었다.
- **추가 결정** (2026-10-21 사용자 확인):
  - 상품 수정에서 이용권 종류(시간권 ↔ 기간권)는 바꿀 수 없다. 종류가 다르면 새 상품으로 등록한다.
  - 이용 중인 좌석은 "이용 불가"로 바꿀 수 없다. 점주가 먼저 수동으로 퇴실 처리(기존 `PATCH /usage-sessions/:sessionId/end`)한 뒤 바꾼다.
    고정석이고 유효 지정이 있으면 FR-022에 따라 이용권 좌석도 먼저 옮기거나 자유석으로 바꿔야 한다.

## R9. 좌석 자체의 타입 변경 가드

- **결정**: 다음 경우 좌석 타입 변경을 거부한다(409).
  - 좌석에 활성 이용 세션이 있음(이용 중). 점주는 먼저 수동으로 퇴실 처리(`PATCH /usage-sessions/:sessionId/end`)한 뒤 바꾼다.
    (2026-10-21 사용자 확인, FR-003. 처음에는 "일시정지 후 변경"이었으나 시간권은 일시정지할 수 없어(R10) analyze 단계에서 정정)
  - 유효한 지정(`HELD`/`ACTIVE`)이 있는 고정석을 자유석으로 변경(spec 경계 상황).

## R10. 일시정지 재개 시 고정석 재지정 (FR-018)

- **결정**: `ResumeTicketDto`에 `seatId`(선택)를 추가한다. 고정석 이용권이면 서비스에서 필수로 검사하고,
  지정할 수 없으면 재개를 거부하고 정지 상태를 유지한다(트랜잭션 롤백).
- **현재 코드 사실(범위 밖)**: 시간권은 입실해도 `ACTIVE`로 바뀌지 않아(`UsageSessionService.createSession`은 기간권만 활성화)
  현재 일시정지할 수 없다(`pauseTicket`은 ACTIVE만 허용). 이 기능에서는 바꾸지 않는다.

## R12. 선점 만료 후 결제 승인 충돌 처리 **[사용자 확인 완료: C + A]**

- **상황**: 결제가 늦어져 선점(HELD)이 만료되고, 그 사이 다른 이용자가 같은 좌석을 선점·확정한 뒤 첫 이용자의 승인 콜백이 온다.
  돈은 결제됐는데 좌석을 줄 수 없다.
- **결정**:
  - **C. 결제 요청 시 사전 차단**: `PaymentService.requestPayment`에서 VAN 요청 전에 주문의 고정석 HELD가 모두 유효한지 확인한다.
    하나라도 만료·해제됐으면 결제 요청을 거부(409)하고 해당 HELD를 `RELEASED(HOLD_EXPIRED)`로 바꾼다. 이용자는 좌석을 다시 고른다.
  - **A. 승인 후 충돌 시 자동 결제 취소(보상 트랜잭션)**: C로도 0이 되지 않는다(결제 요청 후 콜백 전에 만료 가능).
    승인 콜백 처리 트랜잭션에서 이용권은 모두 발급하고, 확정하지 못한 고정석 주문 항목을 모은다.
    커밋 후 그 이용권들에 대해 **기존 환불 경로의 미사용 자동 환불(`processAutoRefund`)** 을 시스템 주체로 호출한다.
    PG 취소 → 콜백 → 이용권 `REVOKED` + 환불 원장 기록까지 기존 흐름을 그대로 탄다.
- **근거**: 결제 후 상품을 제공할 수 없으면 결제를 자동 취소하는 것이 표준이다.
  기존 환불 경로를 재사용하면 환불 락(`RefundLock`)·`PaymentCancel` 처리가 일반 환불과 같아진다.
  정산 원장(`Ledger`) 기록은 일반 환불과 마찬가지로 아직 구현되어 있지 않다(`docs/TODO.md` 환불 미완료 5번).
- **현재 코드 사실**:
  - `RefundService.refund`는 요청자 = 이용권 소유자를 검사한다. 시스템 호출용 공개 메서드 `refundBySystem(ticketId, reason)`을 새로 두고,
    소유자 검사만 건너뛰어 같은 `processAutoRefund`를 쓴다. `PaymentCancel.reason`에 사유를 남긴다.
  - `RefundModule`은 `RefundService`를 export하지 않는다. export를 추가하고 `PaymentModule`이 import한다(순환 의존 없음: 환불 모듈은 결제 모듈을 import하지 않는다).
- **설계상 주의**: 자동 취소가 확정될 때까지 그 고정석 이용권은 **지정 좌석 없이 `UNUSED`로 잠시 존재**한다.
  입실 검증(FR-011)에서 지정 좌석이 없으면 어느 좌석으로도 입실할 수 없으므로 사용될 수 없다.
- **남는 위험 (기존 환불 흐름의 한계)**: PG 취소 요청이 응답 없이 실패하면 `PaymentCancel`이 `REQUESTED`로 남는다.
  기존 흐름은 "다음 환불 요청"이 낡은 락을 정리하는데, 시스템 자동 취소에는 다음 요청이 없다.
  이번에는 거래 로그(`TransactionLoggerService`)에 남겨 운영자가 확인하도록 하고, 자동 재시도는 범위에 넣지 않는다.
  후속 과제로 `docs/TODO.md` 환불 미완료 9번에 기록했다(2026-10-21 사용자 확인).

## R11. 기존 데이터 이전 (FR-016)

- **결정**: 마이그레이션에서 `seats.type`, `products.seat_type`, `order_items.seat_type`, `tickets.seat_type`을
  `NOT NULL DEFAULT 'FREE'`로 추가한다. 기존 행은 모두 자유석이 되고, `SeatAssignment`는 만들지 않는다.
  새 좌석·상품은 DTO에서 타입을 필수로 받는다(FR-002, FR-005).
