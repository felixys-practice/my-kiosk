# 구현 계획: 이용 종료와 환불금 지급 분리

**브랜치**: feature/refund-completion · **갱신일**: 2026-10-26 · **기준**: [spec.md](spec.md), 환불 정책 v0.3

## 요약

환불 검증·동의가 끝나면 이용 종료와 금액을 먼저 확정하고 고정석을 해제한다. PG 결제 취소는 같은 환불 건 아래의 별도 시도로 처리한다. PG 실패로 이용권·좌석을 복구하지 않으며, 미지급액은 자동 조회·재전송과 운영자 재처리로 추적한다. PaymentCancel에는 PG 취소 요청의 번호·금액·처리 결과를 기록하고 Refund·ManualRefundPayout을 추가한다. 실패 확정 뒤 다시 요청하면 기존 실패를 보존하고 새 PG 취소 요청 식별자로 기록한다. 환불 건과 금액은 유지한다. 기존 RefundLock 신규 사용은 상품당 확정 환불 unique·Ticket/Refund 잠금으로 대체한다.

## 기술 환경과 범위

기존 TypeScript·NestJS 11·Prisma 7·PostgreSQL 16·Redis 7·BullMQ 6·Jest 30 구성을 유지한다. 실제 PG·은행 SDK나 새 프레임워크를 도입하지 않는다. 금액·상태·동의·증빙·작업 담당은 PostgreSQL, 실행 예약은 Redis/BullMQ에 둔다. Controller → Service → Repository를 지킨다.

범위는 10개 사용자 스토리, 90개 인수 시나리오, 60개 FR, 25개 SC다. 새 기능은 종료 동의·확정 환불 기록·개별 PG 결과 확인·지급 재처리·별도 환불금 지급 예약/증빙이며, 실송금·PG 수동 성공 변경·일별 대사·초과액 회수·매출/정산 배치는 제외한다.

PG 최종 결과 정상 응답·무적체 조건의 시도 결과 판명 목표는 기본 75초(대기 60+조회 간격 15)다. PG 처리 중·재전송·장애·운영자 확인 중인 미지급액 전체 해결에 이 시간을 보장하지 않는다. 자세한 설정은 [research R10](research.md#r10-설정데이터-전환범위)과 [API 설정](contracts/rest-api.md#8-pg-요청조회복구)을 따른다.

## 1. 이용 종료와 환불 확정

1. 본인/소유 매장 범위에서 대상·결제·기존 확정 환불·가능 조건·금액·사유·필요 동의를 확인한다.
2. Payment → Ticket → TicketPause → UsageSession → SeatAssignment 순서로 필요한 행을 잠그고 다시 검증한다. 거절이면 아무 업무 상태도 바꾸지 않는다.
3. 필요한 퇴실·시간 차감 후 Ticket REVOKED, 기존 정지 기록 closedAt·closeReason 종료, 고정석 해제, 불변 금액의 Refund ACCEPTED와 최초 PaymentCancel을 함께 저장한다. 0원은 PG 취소 요청 없이 PAID·원장 0원을 같은 트랜잭션에 저장한다.
4. PG 호출·종료 Job 제거는 커밋 뒤 수행한다. PG 전송 실패·거절도 업무 확정을 되돌리지 않고 미지급 조치 필요로 남긴다. 접수 응답에는 이용 종료와 환불금 지급 상태를 구분한다.

종료 동의와 기존 이용 중 퇴실 동의는 한 화면 확인으로 전달할 수 있다. 미사용·만료·기존 정지 이용권의 환불 가능 조건을 일반 pauseTicket의 ACTIVE 조건에 종속시키지 않는다.

## 2. PG 결제 취소와 미지급 관리

- Refund는 업무 확정·환불금 지급 합계, PaymentCancel은 시도 상태를 가진다. 성공 실제액·시도 상태·합계·원장·알림은 같은 트랜잭션에서 한 번만 저장한다. 원장은 RELEASABLE이며 고객 은행 명세 반영 시점과는 구분한다.
- 정상 PG 금액이면 PAID, 실제액 불일치면 ACTION_REQUIRED다. 합의액은 불변이며 부족액·초과액을 표시한다. 부족액 전액 PG 재시도는 막고 별도 환불금 지급으로 보충한다. 초과액은 검토 뒤 PAID로 정리하되 금액·원장을 덮어쓰지 않는다.
- 확정 실패 뒤 MANAGER는 사유를 남기고 같은 환불·같은 금액의 취소 요청을 새 PG 취소 요청 식별자로 기록해 보낼 수 있다. 최근 시도가 PG 미접수·자동 재전송 한도 소진으로 실패한 경우에는 해당 매장 점주도 직접 실행할 수 있다. 이전 실패는 보존하고 새 식별자를 발급한 PG 취소 요청에 자동 재전송 한도를 처음부터 적용한다. 미확정 시도·별도 예약이 있거나 이미 일부 지급됐다면 거부한다.
- 송신 결과 미수신은 재조회부터 한다. 백그라운드 자동 작업은 PG 미접수 확정 때만 모든 경로에서 같은 시도 ID·금액으로 한도 내 재전송한다. 한도를 소진한 전송도 PG 미접수가 확인돼야 시도를 FAILED/RETRY_EXHAUSTED로 종료한다. FAILED는 자동 PG 조회·재전송에서 제외하고 Refund ACTION_REQUIRED는 운영자 처리 목록에 남긴다. 결과 불명·PG 처리 중이면 한도 소진 후에도 조회를 이어간다. 확정 시도 실패가 환불금을 포기하는 상태는 아니다.
- 조회 실패 연속 한도는 QUERY_FAILED로 표시한다. DB 일정과 단일 복구 제어 행으로 긴 간격의 가장 오래된 1건 조회→정상 응답 뒤 배치 조회를 실행한다. MANAGER 즉시 재개도 같은 담당 토큰을 사용한다.

점주·MANAGER는 환불 한 건의 미확정 PG 결과를 즉시 확인할 수 있다. 자동 작업과 시도별 담당·최근 조회 시각을 공유해 중복을 막고, 그 건만 기존 결과 처리 규칙으로 반영한다. 전체 복구 재개와 PG 취소 재요청은 분리한다. 개별 확인에서 PG 미접수가 확실하면 자동 재전송 횟수와 관계없이 즉시 다시 보낸다. 미확정 시도는 기존 ID·금액을 사용하고, 한도 소진으로 실패한 시도는 개별 조회 결과를 확인한 뒤 기존 실패를 보존한 새 식별자를 발급한 PG 취소 요청으로 보낸다. 별도 버튼은 요구하지 않는다. 조회 오류·PG 처리 중에는 재전송하지 않는다. 새 환불이나 다른 환불의 배치 조회를 시작하지 않는다. 상세 응답·예외는 [API 계약](contracts/rest-api.md#개별-확인-post-refundrefundidpg-check)을 따른다.

## 3. 별도 환불금 지급 운영

PG 취소 요청들이 모두 최종 상태이고 미지급액이 양수인 조치 필요 건에서만 MANAGER가 별도 환불금 지급을 예약한다. 예약액은 미지급액과 같으며 Refund를 잠그고 RESERVED·MANUAL 전환을 함께 저장해 PG와 다른 환불금 지급을 막는다.

운영자가 실제 지급을 외부에서 마친 뒤 거래 ID·시각·증빙으로 확정한다. 실제 지급·합계·원장을 함께 기록한다. 환불금 지급 여부를 모르면 예약을 유지하고 운영자 확인 대상으로 둔다. 담당 기한이나 단순 대기 시간 때문에 풀지 않는다. 확실한 미지급 증빙이 있어야 예약을 FAILED로 종료한다. 이후 PG 재개도 PG 취소 다시 요청의 명시적 요청이 필요하다. 운영자는 기존 확정 실패 범위에서, 점주는 2절의 최근 시도 RETRY_EXHAUSTED 조건을 만족할 때만 실행한다.

이 기능은 PG 미확정 결과를 수동으로 성공 처리하는 기능이 아니다. 운영자는 새 환불 금액을 정하거나 기존 합의액을 바꿀 수 없다. 실제 은행 송금 실행은 범위 밖이다.

## 4. 동시성·입실·환불금 중복 지급

공유 잠금 순서는 Payment → Ticket → TicketPause → UsageSession → SeatAssignment → Refund → PaymentCancel → ManualRefundPayout이다. 필요한 행만 순서대로 잠그고 동일 종류는 ID 순이다. 기존 정지 기록은 Ticket 다음·UsageSession 이전에 잠그고 처리한다.

입실과 환불 확정은 같은 Ticket을 먼저 잠근다. 환불 확정이 먼저면 모든 환불금 지급 상태에서 TICKET_TERMINATED로 입실을 거부한다. 입실이 먼저면 고객 환불은 사용 이력으로 거절된다. 정지 재개·좌석 타입/배정 변경·자동 종료도 잠금 뒤 REVOKED를 재검증해 종료를 덮어쓰지 않는다.

PG 결과 저장·재시도·별도 환불금 지급은 Refund를 먼저 잠그고 지급들을 확인한다. 활성 PG partial unique와 활성 별도 환불금 지급 partial unique만으로 두 테이블 사이 충돌이 막힌다고 가정하지 않는다. 모든 생성 경로가 Refund 잠금과 상대 지급 검증을 공유한다.

PG 조회 담당 지정은 PaymentCancel만 짧게 갱신하고 끝내며 결과 반영은 별도 트랜잭션이다. PG 호출 중 DB 잠금을 잡지 않는다. 큐·HTTP 멱등 키 만료는 새 환불·환불금 중복 지급의 허용 근거가 아니다.

## 5. 콜백·권한·조회

원문 바이트 HMAC·발송 시각 검증, JWT 없는 두 PG 경로, 동일 canonical과 300초 편차를 유지한다. 사용자 JWT는 PG 서명을 대신하지 않는다. 실제 취소 거래 ID·원승인·Refund 대상을 대조한다.

고객은 본인, 점주는 현재 ShopOwner 매장, MANAGER는 전체 운영 범위다. 기록에는 업무 확정과 PG 취소 요청을 구분해 반환한다. 미지급 목록을 시도 실패로 숨기지 않고 실제 환불금 지급액·미지급액·사유·예약·시도 이력을 표시한다. 알림 읽음은 사람별로 관리한다.

## 6. 데이터 전환·배포

[data-model 10절](data-model.md#10-데이터-전환배포)을 따른다. 미확정 기존 PG 취소 요청이 있으면 전환을 멈추고 조회로 정리한다. 과거 실패·승인 대기를 새 이용 종료 동의로 추정하지 않는다. 증거 있는 성공만 PAID로 이관하고 누락 원장은 중복 없이 보충한다.

종료 시점·상세 ID·응답·동의·실패 의미가 비호환이므로 구/신 서버와 클라이언트를 같은 계약으로 전환한다. 변경 요청과 작업자를 일시 중지해 마이그레이션 검증 뒤 열고, 결과 불명·예약·원장을 지우는 롤백은 하지 않는다. 실제 데이터 전환은 이번 문서 수정에서 실행하지 않는다.

## 구현 순서와 검증

1. 스키마·제약·이관 사전 점검·공통 PG 결과/서명·오류 계약.
2. 종료 동의·고객/매장 판정·원자적 이용 종료·입실/좌석/정지 동시성.
3. 실제 지급·원장·합계·알림·시스템 자동 취소.
4. 조회·재전송·장애 복구·점주/운영자 개별 PG 확인·권한별 PG 취소 재요청.
5. 별도 환불금 지급 예약·증빙·미지급 확인·불일치 검토·권한·읽음.
6. 전체 회귀·중복/경쟁/크래시·빌드·린트·TDD 증거 검증.

각 동작은 헌법의 red/green 순서로 구현한다. [quickstart](quickstart.md)에 모든 인수 시나리오의 HTTP 검증 항목을 둔다. 문서의 링크·식별자·상태·설정·매핑 점검과 실제 구현 정확성·테스트 실행 결과를 구분해 보고한다. 기존 v0.2의 설계 검증 통과 보고를 새 설계의 구현 보증으로 재사용하지 않는다.
