# 구현 완료 후 적용할 변경안: 자동 재전송 종료 후 PG 환불 처리 결과의 개별 확인 허용

작성일: 2026-10-28

## 적용 시점과 문서의 지위

이 문서는 현재 진행 중인 환불 기능의 구현·검증을 모두 마친 뒤 적용할 후속 변경안이다. 현재 구현의 명세나 작업 지시로 사용하지 않는다. 기존 `spec.md`, `plan.md`, `contracts/rest-api.md`, `data-model.md`, `tasks.md`, `tdd/test-list.md`의 구현 기준을 이 문서로 대체하지 않는다.

다른 세션에서 진행하는 기존 작업에는 이 변경을 끼워 넣지 않는다. 기존 구현·검증의 완료 결과와 기준 커밋을 확인한 뒤 별도 후속 작업으로 문서·테스트·코드를 함께 변경한다. 이 문서 작성 시점에는 해당 변경을 구현하거나 검증하지 않았다.

## 변경 목적

이 문서에서 **개별 확인**은 점주·운영자가 특정 환불 건에 대해 PG의 처리 결과를 확인하도록 서버에 요청하는 기능을 뜻한다. 서버는 기존 `PaymentCancel`의 식별자로 PG에 환불 처리 결과를 묻고, PG의 응답에 따라 해당 요청 기록과 환불 건의 상태를 갱신한다. PG가 기존 환불 요청을 접수하지 않았다고 확실히 응답하면 지급 안전 조건을 검사한 뒤 PG에 실제 환불 요청까지 보낸다. **처리 결과를 묻는 요청**과 **결제 취소를 통해 환불을 실행하도록 요구하는 요청**은 서로 다른 동작이다.

현재 설계는 서버의 자동 결과 확인·재전송 대상인 미확정 PG 요청에도 개별 확인을 허용한다. 실제 PG 통신이 진행 중이면 중복 실행을 막지만, 미확정 상태라는 이유만으로 개별 확인을 금지하지는 않는다. 이 때문에 PG가 기존 요청의 미접수를 확인해 주었을 때, 미확정 요청은 기존 식별자로 환불 요청을 다시 보내고 이미 실패 종료된 요청은 새 식별자를 발급해 환불을 요청하는 두 경로를 모두 설명하고 관리해야 한다.

변경 후에는 서버가 자동 재전송 한도를 소진하고 PG 미접수를 확인하여 실패 종료한 요청에 대해서만 점주·운영자가 개별 확인을 실행할 수 있다. 서버가 자동으로 PG 처리 결과를 확인하거나 환불 요청을 재전송하는 동안에는 점주·운영자가 개별 확인을 실행할 수 없다. 개별 확인으로 다시 처리할 PG 요청의 범위를 좁혀, 자동 재전송 한도의 예외와 환불 요청 식별자를 선택하는 동작을 단순화한다.

## 용어와 횟수의 의미

- `Refund`: 이용 종료와 금액이 확정된 환불 건이다. 개별 확인으로 새 환불 신청을 만들거나 이용 종료·금액 확정을 다시 수행하지 않는다.
- `PaymentCancel`: PG에 실제 환불을 요청하는 하나의 시도를 기록한다. 같은 `PaymentCancel.id`로 PG에 환불 요청을 다시 보내는 것과 새 `PaymentCancel` 행을 생성해 새 식별자로 환불 요청을 보내는 것은 구분한다.
- `REFUND_RESEND_LIMIT`: PG가 미접수를 확실히 확인한 동일 환불 요청을 서버가 백그라운드에서 자동 재전송하는 최대 횟수다. 실제 자동 재전송 횟수는 `PaymentCancel.resendCount`에 기록하며 PG에 해당 환불을 최초로 요청한 전송은 세지 않는다. 값이 3이면 최초 전송 1회와 자동 재전송 최대 3회다.
- `QUERY_FAILED`: PG 응답이 없거나 응답 내용으로 환불 처리 상태를 판단할 수 없는 오류가 연속 기준에 도달했을 때, 해당 `PaymentCancel.status`에 기록하는 상태다. `REFUND_QUERY_FAILURE_THRESHOLD`에 따라 이 상태로 전환한 요청은 PG 장애 복구 여부를 확인하는 절차에서 처리 결과를 계속 확인한다. 자동 재전송 한도 소진 후 미접수가 확인되어 `PaymentCancel.status=FAILED`, `failureCode=RETRY_EXHAUSTED`로 종료된 요청과 다르다. 이하 `FAILED / RETRY_EXHAUSTED` 표기는 이 상태·실패 사유의 조합을 뜻한다.

서버는 자동 재전송 횟수를 소진했다는 이유만으로 해당 환불 요청의 자동 처리를 종료하지 않는다. PG가 해당 환불을 처리 중이라고 응답하거나 서버가 PG의 처리 결과를 확인하지 못하면, 서버는 기존 자동 확인·장애 복구 확인 절차에 따라 해당 환불의 처리 결과를 계속 확인한다. 한도 소진 후 PG가 해당 요청의 미접수를 확실히 확인해 주어야 서버는 그 `PaymentCancel`을 `FAILED / RETRY_EXHAUSTED`로 종료한다.

## 현재 기준과 변경할 동작

아래의 현재 기준은 구현 완료 여부가 아니라 기존 문서에 정의된 동작을 뜻한다.

| 대상 | 현재 문서의 기준 | 후속 변경안 |
|---|---|---|
| 최근 `PaymentCancel`이 `REQUESTED` 또는 `QUERY_FAILED` | 점주·운영자의 PG 처리 결과 확인을 허용. PG 미접수 확인 시 자동 한도와 관계없이 기존 식별자로 환불 요청을 재전송 | 점주·운영자의 개별 확인을 허용하지 않음. 서버가 자동 확인·재전송·장애 복구 확인 절차로 해당 환불 요청을 계속 처리 |
| 최근 `PaymentCancel`이 `FAILED / RETRY_EXHAUSTED` | 조건 충족 시 점주·운영자의 PG 처리 결과 확인과 새 환불 요청 기록 생성 허용 | 점주·운영자의 개별 확인 허용. PG가 기존 요청의 미접수를 다시 확인해 주면 지급 안전 조건을 검사하여 새 `PaymentCancel`을 생성하고 PG에 실제 환불 요청 전송 |
| 최근 `PaymentCancel`이 `FAILED / SEND_FAILED` 또는 `FAILED / PG_REJECTED` | 조건 충족 시 점주·운영자의 PG 처리 결과 확인 허용 | 자동 재전송 한도 소진으로 종료된 요청이 아니므로 점주·운영자의 개별 확인을 허용하지 않음 |

변경 후에는 개별 확인 버튼의 표시·활성 조건뿐 아니라 `POST /refund/:refundId/pg-check`에서 서버가 PG 처리 결과 확인을 허용하는 조건도 같은 범위로 제한한다. 버튼만 비활성화하면 클라이언트가 API를 직접 호출하여 대상이 아닌 환불의 개별 확인을 실행할 수 있으므로, 서버도 해당 요청을 제한해야 한다. 실제 화면이 없는 경우에도 서버 계약과 테스트에 이 조건을 적용한다.

최근 `PaymentCancel`의 실패 사유가 `SEND_FAILED`·`PG_REJECTED`인 환불에 대해 점주가 PG 처리 결과를 개별 확인할 수 없게 되는 것은 기존 기준 대비 업무 동작의 변경이다. 이 사유의 요청에도 개별 확인을 허용하면 이번의 “한도 소진 종료 후에만 허용” 범위가 넓어지므로 별도 결정 없이 포함하지 않는다. 운영자 전용 직접 재시도인 `POST /refund/:refundId/payout-retries`의 기존 권한·조건은 이번 변경으로 바꾸지 않는다.

## 변경 후 특정 환불의 PG 처리 결과를 확인하고 환불을 다시 요청하는 흐름

1. 점주·운영자가 특정 환불의 개별 확인을 요청하면, 서버는 해당 매장 점주 또는 운영자의 권한을 확인한다. 서버는 해당 환불의 최근 `PaymentCancel`이 `FAILED / RETRY_EXHAUSTED`이고 그 환불의 지급을 재처리할 수 있는지 검사한다. 자동 재전송 횟수가 한도에 도달했더라도 최근 `PaymentCancel`이 미확정 상태라면 서버는 개별 확인을 허용하지 않는다.
2. 서버는 같은 환불의 PG 환불 요청 전송·결과 확인과 다른 지급 처리가 중복 실행되지 않도록 기존 DB 잠금·담당 토큰·처리 기한을 사용한다. 담당 토큰·처리 기한은 사람이 아니라 해당 요청을 실행하는 서버 코드에 부여하는 실행 권한이다. 반복 클릭·동시 요청으로 같은 환불을 중복 처리하거나, 실행 권한이 만료된 서버 코드가 PG 결과를 뒤늦게 반영하지 못하도록 하는 보호 장치는 유지한다.
3. 서버는 실패 종료된 기존 `PaymentCancel.id`를 사용하여 PG에 그 요청의 환불 처리 결과를 한 번 묻는다. 이 단계에서는 PG에 결제 취소를 실행하라는 환불 요청을 보내지 않는다.
4. PG가 기존 환불 요청을 접수하지 않았다고 확실히 응답하면, 서버는 해당 환불의 실제 지급액이 0원인지, 다른 미확정 지급과 활성 별도 지급 예약이 없는지, 지급 방식이 PG인지, 저장된 PG 결과 사이에 모순이 없는지, 현재 실행에 부여된 담당 토큰이 유효한지 등 기존 지급 안전 조건을 다시 검사한다.
5. 서버는 조건을 충족한 환불의 기존 `PaymentCancel`에 기록된 실패 상태·사유·횟수를 보존하고, 같은 `Refund`와 같은 환불 금액으로 새 `PaymentCancel`을 생성한다. 기존 요청의 상태 확인에 부여한 실행 권한을 해제하고 새 요청의 전송에 실행 권한을 부여하는 변경은 같은 트랜잭션에서 저장한다. 커밋 후 서버는 새 `PaymentCancel.id`를 사용해 PG에 실제 환불 요청을 보낸다.
6. 새 `PaymentCancel`의 `resendCount`는 0부터 시작한다. 서버는 새 요청의 최초 전송을 제외한 이후 백그라운드 자동 재전송에 기존 `REFUND_RESEND_LIMIT`을 적용한다. 이전 `PaymentCancel`의 재전송 횟수를 초기화하거나 새 기록으로 옮기지 않는다.
7. 서버가 PG 응답을 받지 못하거나 그 응답으로 기존 요청의 환불 처리 상태를 판단하지 못하면, 기존 `PaymentCancel`의 실패 이력을 유지하고 새 `PaymentCancel`을 만들지 않는다. PG가 환불 성공·처리 중 등 기존 실패 확정과 모순되는 결과를 반환하면, 서버는 기존 결과 모순 처리 규칙에 따라 모순 내용을 기록하고 운영자에게 알리며 해당 환불의 추가 지급을 차단한다. 이미 실패 종료된 `PaymentCancel`을 자동 상태 확인·환불 요청 재전송 대상으로 임의 복귀시키지 않는다.

PG에 새 환불 요청을 보낸 뒤 새 `PaymentCancel`이 미확정 상태가 되면, 점주·운영자는 해당 환불의 개별 확인을 다시 실행할 수 없다. 서버가 새 요청의 자동 재전송 한도를 소진하고 PG 미접수를 확인하여 그 기록을 `FAILED / RETRY_EXHAUSTED`로 종료하면, 점주·운영자는 해당 환불의 PG 처리 결과를 다시 개별 확인할 수 있다.

## 후속 작업에서 맞출 문서·구현·검증 범위

기존 구현 완료 후 아래 위치를 실제 완료 상태와 다시 대조한다. 기존 완료 작업을 미완료로 되돌리거나 기존 검증 결과를 덮어쓰지 말고, 변경 전 기준을 보존한 채 후속 작업과 검증을 추가한다.

- `spec.md`: US5·US10, FR-052·FR-054·FR-057 등 점주·운영자가 PG 처리 결과를 개별 확인할 수 있는 환불의 범위와 기존 식별자로 환불 요청을 재전송하던 한도 예외를 수정한다. 자동 처리 중인 환불에도 개별 확인을 허용하던 인수 조건·성공 기준도 함께 맞춘다.
- `contracts/rest-api.md`: §8의 `pg-check` 실행을 허용할 환불의 범위, 허용 대상이 아닌 환불에 대한 응답, PG 미접수 확인 후 새 `PaymentCancel`을 생성하는 규칙을 맞춘다. 허용 대상이 아닌 환불의 요청을 거부할지 저장 상태를 반환할지 등 구체적인 응답 계약은 기존 응답 형식과 대조하여 후속 설계에서 정한다.
- `plan.md`, `data-model.md`: 개별 확인에서 미확정 `PaymentCancel`의 식별자로 PG에 환불 요청을 다시 보내는 경로를 제거하고, 실패 종료된 기록을 보존한 채 새 `PaymentCancel`을 생성하여 PG에 환불을 요청하는 경로로 정리한다. `manualResendCount`의 남은 사용처를 확인하되, 이 문서만을 근거로 필드를 삭제하지 않는다.
- `tasks.md`, `tdd/test-list.md`: T101·T102·T130 등 관련 작업과 연결된 단위·통합·인수 테스트를 추적하여 후속 변경 작업·검증 조건을 추가한다. 작업 ID는 적용 시점의 문서와 다시 확인한다.
- 개별 확인 API·서비스와 자동 작업 선택 로직: 개별 확인을 허용할 환불의 범위, 같은 환불의 중복 실행 방지, 기존 `PaymentCancel`의 실패 이력 보존, 새 `PaymentCancel` 생성, 새 요청에 대한 자동 재전송 한도 적용을 함께 반영한다.
- `.env.example` 및 관련 운영 설명: “개별 확인에 따른 재전송은 한도에서 제외”라는 설명을 “서버가 자동 재전송 한도 소진과 PG 미접수 확인으로 기존 요청을 실패 종료한 뒤, 점주·운영자의 개별 확인 결과에 따라 새 PG 환불 요청을 생성하고 새 요청에 자동 한도를 적용”하는 설명으로 바꾼다.

후속 구현에서는 다음 동작을 검증한다.

- 서버가 최근 `PaymentCancel`이 `REQUESTED`·`QUERY_FAILED`인 환불의 개별 확인을 실행하지 않는다. 자동 재전송 횟수만 소진하고 요청이 미확정이면 개별 확인을 허용하지 않는다.
- 최근 `PaymentCancel`이 `FAILED / RETRY_EXHAUSTED`인 환불에 대해, 서버가 PG 미접수를 다시 확인하고 지급 안전 조건을 검사한 뒤 새 `PaymentCancel`을 정확히 1건 생성한다. 이전 기록의 자동 재전송 횟수를 보존하고 새 기록의 자동 재전송 횟수는 0으로 저장한다.
- 버튼 동시 클릭, 다른 지급 처리와의 경쟁, PG 결과 확인 오류, 기존 실패 이력과 모순되는 PG 응답이 발생해도 서버가 해당 환불을 중복 지급하지 않는다.
- 서버가 최근 `PaymentCancel`의 실패 사유가 `SEND_FAILED`·`PG_REJECTED`인 환불의 개별 확인을 실행하지 않는다. 운영자가 `payout-retries`로 직접 환불을 재시도하는 기존 기능은 유지한다.
