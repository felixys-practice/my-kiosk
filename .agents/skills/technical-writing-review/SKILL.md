# 한국어 기술 문서 검수

독자가 대화 이력을 몰라도 대상·조건·동작을 이해할 수 있는지 확인한다.
의미 전달과 의미 보존을 따로 검토한다. 기술 용어를 없애거나 문장을 무조건 늘리지 않는다.

## 역할과 권한

이 스킬에서 “작성 에이전트”는 사용자와 대화하며 문서를 작성·수정하는 현재 에이전트를 뜻한다. 작성용 에이전트를 별도로 생성하지 않는다. 검수 담당만 별도 서브 에이전트로 생성한다.

- 작성 에이전트는 검수 요청과 결과 판단·수정을 담당한다. 검수자의 필수 산출물은 근거 있는 문제 지적과 보완할 정보이며, 완성된 수정 문장이 아니다.
- 검수 서브 에이전트는 이 스킬을 읽고 읽기 전용으로 검수한다. 파일 수정, 테스트·서버·시드 실행, DB 변경, 커밋은 하지 않는다. 다른 에이전트를 생성하지 않는다.
- 검토 요청만 받은 경우 작성 에이전트도 수정하지 않는다. 문서 작성·수정이 승인된 범위에서만 검수 결과를 반영하고, 별도 단계 승인 조건을 유지한다.
- 이 스킬 생성만으로 다른 문서의 검수를 실행하거나 자동 실행 훅을 추가하지 않는다.

## 작성 에이전트의 검수 요청

1. 대상 파일·절 또는 변경 범위, 독자 수준, 필요한 기준 문서와 합의한 제약을 정한다. 기존 작업 트리 변경은 보존한다.
2. 대화 이력을 상속하지 않는 별도 서브 에이전트를 생성한다. `fork_turns`를 지원하면 `none`을 사용한다. 스킬의 절대 경로, 대상, 독자, 기준 문서, 읽기 전용 조건을 전달한다.
3. 기대하는 지적이나 이전 결론은 주입하지 않는다. 대화에서만 확정한 필수 제약은 사실로 구분해 전달하되 독자가 이를 알고 있다고 가정하지 않게 한다.
4. 검수 에이전트는 아래 절차를 수행하고 결과를 반환한다. 도구가 없어 별도 에이전트를 사용할 수 없으면 독립 검수를 했다고 주장하지 말고 자체 검토와 구분한다.

요청 예시:

```text
당신은 읽기 전용 문서 검수 담당이다. 다른 에이전트를 생성하지 않는다.
이 스킬을 읽고 검수 절차와 결과 형식을 따른다: <SKILL.md 절대 경로>
대상: <파일과 절 또는 변경 범위>
독자: <예: 프로젝트를 처음 읽는 개발자>
기준 문서: <파일 경로>
합의한 제약: <필요한 사실만>
파일을 수정하지 말고 검수 결과만 반환한다.
```

## 검수 서브 에이전트의 절차

### 근거 확인

- 적용되는 `AGENTS.md`와 `~/.codex/instructions/korean-technical-writing.md`를 읽고 따른다.
- 대상 문장과 해당 절·인접 문맥을 읽는다. 판단에 필요한 정의·참조 문서의 실제 내용을 확인한다.
- 현재 동작 설명은 필요한 구현·호출처를, 미래 설계 설명은 승인된 명세를 기준으로 판단한다. 현행 코드와 다르다는 이유만으로 미래 설계를 오류로 보지 않는다.
- 수정 전후 자료가 있으면 비교한다. 자료가 없으면 의미 보존을 확인하지 못한 범위를 남긴다.

### 의미 전달 검수

- 어떤 객체·요청·상태인지, 누가 어떤 조건에서 무엇을 하는지 문장이나 인접 문맥에서 알 수 있는가?
- “승인 대기”처럼 대상이 빠지거나 “기존 계약대로”라는 참조가 실제 처리 설명을 대신하는가?
- “책임 중복”, “호출 경계”, “구형 경로”가 필요한 코드 관계·동작을 숨기는가?
- 나열한 항목의 기준과 목적어가 일치하는가? 보내는 행위와 취소 업무처럼 기준이 다른 동작을 설명 없이 묶지 않았는가?
- 정의·상태·처리 규칙·검증 방법이 섞여 관계가 불분명한가? 필요하면 레이아웃을 나눈다.
- 독자에게 필요한 용어 정의가 있는가? 실제 코드 식별자와 통상적인 기술 용어는 유지한다.

“결제 승인 대기”처럼 짧아도 명확한 표현은 늘리지 않는다. 개인적인 문체 선호는 지적하지 않는다. 독자가 무엇을 추측하거나 오해하는지 설명할 수 있을 때만 발견 사항으로 보고한다.

### 의미 보존 검수

- 검수 대상의 수정 전후 문장과 선택적으로 제시하는 수정 예시가 업무 조건·권한·대상·상태·금액·트랜잭션·커밋 순서·멱등성·동시성·복구 규칙을 바꾸지 않는지 확인한다.
- 코드 식별자와 객체 소속을 유지하고 구현 사실·확정 설계·제안을 구분한다.
- 빠진 조건을 추측해서 보충하지 않는다. 의미를 확정하려면 확인이 필요한 경우 수정 예시 대신 질문을 남긴다.
- 오탈자나 대상이 확실한 표현 교정처럼 근거만으로 의미를 확정할 수 있을 때만 수정 예시를 선택적으로 제공한다.
- 무엇을 명시해야 하는지 구체적으로 지적한다. 수정 예시를 제공할 때도 빠진 의미만 최소한으로 보충하고, 길어진 문장을 개선의 증거로 삼지 않는다.

## 검수 결과 형식

같은 원인과 수정으로 해결되는 지적은 묶고, 각 발견 사항을 아래 형식으로 반환한다.

```text
ID: TW-001
위치: 파일:행과 절
원문:
문제: 독자가 추측해야 하는 정보 또는 오해할 수 있는 동작
구분: 의미 전달 / 의미 보존 / 둘 다
보완할 정보: 독자가 이해하려면 무엇이 명시되어야 하는가?
확인할 질문: 의미를 확정하려면 확인이 필요한 경우 작성
수정 예시 — 선택: 근거만으로 의미를 확정할 수 있을 때 제공
근거: 확인한 문서·코드 위치 또는 해당 절의 문맥
설계 결정 필요 여부: 없음 / 필요 — 결정할 사항
```

읽은 범위·확인하지 못한 범위와 남은 문제를 요약하고 마지막 줄을 `통과` 또는 `수정 필요`로 끝낸다. `통과`는 지정 범위의 문서 검수 결과이며 구현·런타임 검증 통과가 아니다. 필수 의미를 확인할 근거가 부족한 경우도 해결할 사항으로 남긴다.

## 작성 에이전트의 반영과 재검수

1. 지적별 문제·근거·보완할 정보를 확인하고 `수용`, `미수용 — 이유`, `사용자 결정 필요`로 판단한다. 지적을 무조건 적용하지 않는다.
2. 작성 에이전트가 의도와 근거를 확인하여 수정 문장을 작성한다. 검수자의 수정 예시가 있어도 그대로 채택하지 말고 의미 보존 여부를 확인한다. 승인된 범위의 수용 항목만 수정한다. 새 설계 결정은 질문하고 임의로 확정하지 않는다.
3. 같은 검수 에이전트에 판단과 수정 위치를 전달하여 수정 부분·인접 문맥을 재검수하게 한다. 관련 없는 범위로 넓히지 않는다.
4. 최초 검수 후 수정·재검수는 기본 최대 2회로 제한한다. 미해결 문제나 결정이 남으면 보고하고 추가 범위를 정한다. 횟수 소진을 통과로 처리하지 않는다.
5. 최종 응답에 수정 내용, 검수 범위·결과, 미해결 항목·미확인 범위를 간결하게 보고한다.
