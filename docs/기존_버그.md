# 기존 버그

이 기능 이전부터 있던 버그 중 기능 작업 중에 확인한 것을 모아둔다.
각 기능은 범위 밖 문제를 고치지 않으므로(헌법 원칙 V) 여기에 기록하고, 이후 `/speckit-specify`로 별도 작업을 시작한다.
고친 항목은 이 문서에서 지우고, 고친 기능의 spec 디렉터리를 커밋 메시지에 남긴다.

항목마다 현상, 근거(코드 위치), 재현 방법, 영향, 발견 경위를 적는다.

---

## 2. 활성화 전 기간권을 조회하면 500

- **현상**: 결제 후 아직 입실하지 않은 기간권(`UNUSED`, `expiresAt = null`)을 조회하면 `Error('정기권에서 expiresAt 값은 필수입니다')`가 그대로 던져져 500이 된다.
- **근거**: [ticket.service.ts](../src/ticket/ticket.service.ts) 기간권 응답 변환의 `if (!ticket.expiresAt) throw new Error(...)`
- **재현**: 기간권 결제 → 입실 없이 `GET /tickets/:id` → 500
- **영향**: 구매 직후 기간권을 볼 수 없다. 활성화 전에는 `activationDeadline`을 보여 주는 등 응답 형태를 정해야 한다.
- **발견**: 001-seat-type QS-10(시간권으로 대신 검증, [seat-type.e2e-spec.ts](../test/seat-type.e2e-spec.ts) QS-10 주석)

## 3. 주문 금액에서 할인이 두 번 빠진다

- **현상**: 주문 항목의 `amount`를 이미 `원가 - 할인`으로 저장하는데, 주문 합계(`totalAmount`)를 계산할 때 `amount - discountAmount`로 할인을 한 번 더 뺀다.
- **근거**: [order.service.ts](../src/order/order.service.ts) `createOrder`의 주문 항목 `amount: foundProduct.amount - discountAmount`와 합계 `acc.totalAmount + orderItem.amount - orderItem.discountAmount`
- **재현**: 현재는 `discountAmount = 0`으로 고정이라 드러나지 않는다. 할인을 도입하면 합계가 할인액만큼 더 작아진다.
- **영향**: 할인 도입 시 결제 금액·정산 금액이 틀어진다.
- **발견**: 001-seat-type US2 주문 작업

## 4. 상품 목록의 전체 개수(total)가 필터와 맞지 않는다

- **현상**: 목록은 매장·이용권 종류로 거르지만, 전체 개수는 조건 없이 모든 상품을 센다.
- **근거**: [product.repository.ts](../src/product/product.repository.ts) 목록 조회의 `findMany({ where: { shopId, ticketType } })`와 `this.prisma.product.count()`
- **재현**: 매장 2곳에 상품을 등록하고 한 매장의 목록 조회 → `meta.total`이 두 매장 합계
- **영향**: 페이지 수 계산이 틀린다.
- **발견**: 001-seat-type US2 상품 작업

## 5. 결제 요청 실패 시 `throw Error;`로 생성자 자체를 던진다

- **현상**: VAN 요청이 실패하면 결제를 실패 처리한 뒤 `throw Error;`를 실행한다. 오류 객체가 아니라 `Error` 생성자를 던지므로 메시지·스택이 없고, 전역 필터가 도메인 오류로 변환하지 못한다.
- **근거**: [payment.service.ts](../src/payment/payment.service.ts) `requestPayment`의 "payment 요청 실패 상태 업데이트" 다음 줄
- **재현**: `requestVan`이 예외를 던지게 하고 `POST /payments` → 원인 정보 없는 500
- **영향**: 클라이언트가 결제 실패 사유를 구분할 수 없다(헌법 VI 오류 응답과 맞지 않음).
- **발견**: 001-seat-type US2 결제 작업

## 6. 상품 수정에서 구매 시간·구매 기간의 범위 검증이 동작하지 않는다

- **현상**: `UpdateProductDto`는 `CreateProductDto`에서 `type`을 뺀 DTO다. `purchasedMinutes`·`purchasedDurationDays`의 검증은
  `@ValidateIf(dto.type === ...)` 조건 아래에 있는데 수정 요청에는 `type`이 없어 조건이 항상 거짓이므로, `@Min`·`@Max`가 실행되지 않는다.
  (`amount`·`usableDays`처럼 조건이 없는 필드는 검증된다.)
- **근거**: [update-product.dto.ts](../src/product/dto/update-product.dto.ts)의 `PartialType(OmitType(CreateProductDto, ['type']))`,
  [create-product.dto.ts](../src/product/dto/create-product.dto.ts)의 `@ValidateIf`
- **재현**: `PATCH /shops/:shopId/products/:productId`(시간권 상품)에 `purchasedMinutes: 1` → 생성 시 최솟값(10) 미만인데 수정됨
- **영향**: 잘못된 이용 시간·기간의 상품이 판매될 수 있다.
- **발견**: 001-seat-type T058(사용자 결정: 이번 범위에서 추가하지 않음)

## 9. 좌석 타입 E2E가 가끔 401·403·400·404로 실패한다

- **현상**: E2E 전체(`npm run test:e2e`)를 반복하면 `test/seat-type.e2e-spec.ts`의 여러 테스트가 가끔 실패한다. 실패하는 테스트는 실행마다 다르다(QS-4·6·8·9·10·12·13·16a·19·20·23·24·25 등). 주로 준비 단계의 주문·결제·입실 요청에서 기대와 다른 응답(401, 403, 400, 404, 500)을 받는다. 병렬 실행과 순차 실행(`--runInBand`) 모두에서 생기고, 파일만 단독으로 실행해도 생긴다.
- **근거**
  - 입실 API의 외부 API 스텁: [usage-session.service.ts](../src/usage-session/usage-session.service.ts) `mockExternalApi`는 운영 코드 안에서 대기 후 `Math.random()`으로 무작위 실패하고, `withRetry`로 최대 3회 재시도한다. 모두 실패하면 세션을 실패 처리하고 500을 낸다.
  - 스텁의 실패 확률을 `0.0`으로 바꿨을 때는 E2E 전체 병렬 15회, 순차 5회가 모두 통과했다. 확률 `0.1`에서는 병렬 15회 중 4회, 순차 5회 중 2회 실패했다.
  - 401은 [jwt.strategy.ts](../src/auth/strategies/jwt.strategy.ts) `validate`에서 Redis의 세션 취소 시각(`RedisKeys.sessionRevoked`)보다 먼저 발급된 토큰일 때 난다.
  - 스텁의 무작위 실패가 어떤 경로로 401·403·404로 이어지는지는 확인하지 않았다.
  - 단위 테스트는 `jest.spyOn(Math, 'random').mockReturnValue(0.99)`로 스텁을 항상 성공하게 고정하지만, E2E는 고정하지 않는다.
- **재현**: `npm run test:e2e`를 15회 정도 반복 → 몇 회 실패(실패하는 테스트는 매번 다름)
- **영향**: E2E 통과를 완료 기준으로 믿을 수 없다. 실패할 때마다 이번 변경 탓인지 기존 문제인지 따로 가려야 한다. 또한 입실 실패 시의 재시도·보상 로직(세션 실패 처리, Job 취소)은 무작위로만 실행되어 테스트로 검증되지 않는다.
- **함께 볼 것**: 업계 표준 해결은 외부 장치 API를 provider로 분리하고, 테스트에서는 `overrideProvider`로 성공·실패를 직접 지정하는 것이다. 운영 코드 안의 무작위 스텁이 없어진다.
- **발견**: bug time-pass-pause-rejected 검증([test.md](../.specify/bugs/time-pass-pause-rejected/test.md)). `main`(수정 전)에서도 같은 파일이 10회 중 1회 실패(QS-13)한 것을 확인했다
