# 환불을 상품(OrderItem) 단위로 추적하는 구조

`PaymentCancel`이 `orderItemId` FK로 대상 상품을 직접 참조한다.

## 기존 구조의 한계

```
Order 1:N OrderItem   (주문 상품)
Order 1:N Payment     (결제, 재시도 지원)
Payment 1:N PaymentCancel  (PG 취소 요청)
```

`OrderItem`과 `Payment`/`PaymentCancel` 사이에는 직접적인 연결이
없다. 둘 다 `Order`를 거쳐야만 만난다. 그래서 "이 상품이
환불됐는가"라는 질문에 스키마가 답을 할 수 없었다. `PaymentCancel`은
"이 결제에서 얼마를 취소했다"는 금액만 알 뿐, 그 취소가 정기권
때문인지 시간권 때문인지는 기록되지 않는다.

매장별 상품 판매 순위처럼 "실제로 판매된 상품"을 집계하려면 환불된
상품을 제외해야 하는데, 이 연결이 없으면 정확한 집계가 불가능하다.

## 해결: `PaymentCancel`에 `orderItemId` 직접 참조

```
Payment 1:N PaymentCancel                (기존)
OrderItem 1:N PaymentCancel              (orderItemId FK 추가)
```

`PaymentCancel`이 `orderItemId` FK를 직접 갖는다. 한 번의 환불
신청은 항상 상품 1건만 대상으로 하고([환불_정책.md §0](./환불_정책.md#0-환불의-시작점--order-orderitem-ticket) 참고),
하나의 상품은 환불 1회로 종료되므로(SUCCEEDED 시 Ticket이 즉시
REVOKED로 전이), 관계는 실질적으로 1:1에 가깝다. 스키마상 N:1인
이유는 취소 시도가 실패(`FAILED`) 후 재시도될 수 있기 때문이다.

```prisma
model PaymentCancel {
  // ... 기존 필드 ...
  orderItemId String    @map("order_item_id")
  orderItem   OrderItem @relation(fields: [orderItemId], references: [id])

  @@index([orderItemId])
}
```

### 왜 중간 테이블(join table)이 아닌 직접 FK인가

초기 설계에서는 `PaymentCancelItem`이라는 중간 테이블을 두어
`PaymentCancel`과 `OrderItem`을 M:N으로 연결했다. 그 근거는
"여러 상품을 한 번에 묶어 취소하는 경우 `PaymentCancel` 1건에
상품 N건이 딸린다"는 가정이었다.

그러나 이 프로젝트의 환불 API는 `ticketId` 단건만 받고, 여러
상품을 한 번의 PG API 호출로 묶어 취소하는 시나리오를 다루지
않는다([환불_정책.md §0](./환불_정책.md#0-환불의-시작점--order-orderitem-ticket)).
관계가 항상 1:1이므로 M:N을 표현할 중간 테이블은 불필요한
복잡성이다. 직접 FK로 충분하다.

"결제=Order 단위 / 환불 판단=OrderItem 단위"라는 비대칭은 여전히
존재하지만, 이 비대칭이 요구하는 것은 `PaymentCancel`이
`OrderItem`을 **참조**하는 것이지, 별도의 연결 모델을 두는 것이
아니다. FK 하나면 그 참조가 성립한다.

## 업계 사례

Stripe의 `credit_note_line_item`, Shopify의 `RefundLineItem`은
M:N 관계를 위한 별도 line item 모델을 둔다. 이 프로젝트가 다른
패턴을 선택한 이유는, 위 서비스들은 하나의 환불에 여러 상품을
묶는 다건 환불을 지원하지만 이 프로젝트는 단건 환불만 다루기
때문이다. 요구사항이 다르면 구조도 달라야 한다.

이 프로젝트는 나이스페이/KCP/KSNET 등 국내 VAN사를 연동하므로,
국제 사례의 `Refund` 대신 국내 PG API 관례를 따라 `PaymentCancel`
이름을 유지했다.
