## 2. `PaymentCancel`이 `orderItemId`를 직접 참조하는 이유

```
Payment 1:N PaymentCancel            (결제 단위)
OrderItem 1:N PaymentCancel          (상품 단위 — orderItemId FK)
```

### 질문: 왜 중간 테이블(join table)이 아닌 직접 FK인가?

**결제(Payment)와 환불(Refund)은 원래 단위가 다르다.** "결제=Order
단위 / 환불 판단=OrderItem 단위"라는 비대칭이 존재한다. 이 비대칭은
`PaymentCancel`이 `OrderItem`을 **참조**해야 하는 근거이지만, 그
참조가 반드시 별도의 연결 모델을 요구하지는 않는다.

> **결제(Payment)는 "돈이 오간 사실"이고, 환불(Refund)은 "무엇에 대해
> 돈을 돌려주는가"라는 계약상의 판단이다.**

- 결제는 금전적 사건 하나라 쪼갤 이유가 없다. PG 승인은 주문
  전체 금액에 대해 한 번 이뤄지므로 `Payment`는 **주문(Order) 단위**로
  존재한다.
- 반면 환불 여부는 상품마다 사정이 다르다(이 프로젝트 기준: 정기권은
  활성화 여부, 시간권은 사용량). 그래서 환불 결정은 **상품(OrderItem)
  단위**로 이뤄진다.

### 왜 M:N이 아닌가

초기 설계에서는 `PaymentCancelItem`이라는 중간 테이블을 두어
`PaymentCancel`과 `OrderItem`을 M:N으로 연결했다. 그 논거는
두 방향이었다.

1. **PaymentCancel → OrderItem**: 여러 상품을 한 번에 묶어 취소하면
   `PaymentCancel` 1건에 상품 N건이 딸린다.
2. **OrderItem → PaymentCancel**: 한 상품에 대해 잔여 사용량 비례로
   여러 번 나눠 취소될 수 있다.

두 논거 모두 이 프로젝트에서는 성립하지 않는다.

- **(1) 다건 묶음 취소 불가**: 환불 API는 `ticketId` 단건만 받으며,
  여러 상품을 한 번의 PG 호출로 묶어 취소하는 시나리오를 다루지
  않는다([환불_정책.md §0](./환불_정책.md#0-환불의-시작점--order-orderitem-ticket) 참고).
- **(2) 다회 부분 환불 폐기**: 하나의 상품에 대한 환불은 딱 한 번만
  일어나고 그 즉시 `Ticket`이 `REVOKED`로 종료된다(2026-09-05 재검토
  결론, 2026-09-06 코드 반영 완료).

관계가 항상 1:1이므로 직접 FK(`PaymentCancel.orderItemId`)로 충분하다.
중간 테이블은 불필요한 복잡성이었다.

> **✅ 반영 완료(2026-09-07)**: `PaymentCancelItem` 모델을 삭제하고,
> `PaymentCancel`에 `orderItemId` FK를 직접 추가했다. 스키마, 리포지토리,
> 서비스, 시드 데이터 모두 갱신 완료.

### 왜 `OrderItem`이 `Payment`를 직접 참조하지 않는가

"PaymentCancel이 아니라 `OrderItem`에 `paymentId`를 직접 두면 안
되나?"라는 질문이 나올 수 있는데, 이 방향은 애초에 성립하지 않는다.
결제는 상품이 아니라 **주문 단위로 실행**되므로, `OrderItem`이
`Payment`를 직접 참조하면 같은 주문의 여러 상품이 같은 `paymentId`를
중복 저장하는 비정규화가 될 뿐이다. PG가 "이 승인 금액이 어느 상품
몫이다"라는 정보를 애초에 주지 않는 경우가 많아, 결제 시점에는
구할 수조차 없는 정보이기도 하다.

### 업계 사례와의 차이

Stripe의 `credit_note_line_item`, Shopify의 `RefundLineItem`은
별도 line item 모델을 둔다. 이 서비스들은 하나의 환불에 여러 상품을
묶는 다건 환불을 지원하기 때문에 M:N 연결 모델이 필요하다. 이
프로젝트는 단건 환불만 다루므로 직접 FK로 충분하다. 요구사항이
다르면 구조도 달라야 한다.
