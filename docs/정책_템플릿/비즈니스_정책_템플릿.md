# 비즈니스 정책 문서 템플릿

> 도메인(환불, 정산 등)의 **운영 비즈니스 정책**을 같은 구조와 기준으로 쓰기 위한 템플릿이다. 이 문서는 정책이 아니라 **작성 가이드**다.
>
> - 사용법: 아래 "템플릿 본문"을 복사해 `{도메인}_비즈니스_정책.md`로 만들고, `> 작성 가이드` 인용문과 **작성 예**는 지우고 `{ }` 자리를 채운다.
> - 절 표시: **(필수)** 항상 둔다 / **(없으면 한 줄)** 내용이 없으면 "…은 없다"고 한 줄로 남긴다. "없다"는 것 자체가 정책이고, 빠져 있으면 깜빡 잊은 것과 구분되지 않기 때문이다 / **(선택)** 해당하는 내용이 있을 때만 둔다. 실제 정책 문서에서는 이 표시를 지운다.
> - 작성 예: 모든 절의 작성 예는 **하나의 가상 사례("이용권 환불 정책 v1")**다. 실제 정책이 아니며, 절끼리 서로 이어진다. 끝의 [작성 예 따라 읽기](#작성-예-따라-읽기)에서 판정 하나를 처음부터 끝까지 따라가 볼 수 있다.
> - 최종 수정: 2026-10-20

---

## 공통 작성 규칙

### 1. 정책 문서에 쓰는 것과 쓰지 않는 것

정책 문서는 **무엇을, 언제, 누가 결정하는가**를 기획·운영·개발이 함께 읽을 수 있게 적는다. 구현 방법은 적지 않는다.

| 정책 문서에 쓴다 | 다른 문서로 보낸다 |
|---|---|
| 판정 규칙(조건 → 결과), 결과별로 고객이 겪는 일, 금액 규칙, 기준값, 거절 사유와 안내 문구 | 테이블·컬럼·쿼리, 트랜잭션, 락, API 설계 → **설계서** |
| 결정이 필요한 항목(`D-xx`)과 선택지 | 선택지별 장단점, 검토 의견, 기존 설계와의 대조 → **검토 메모** |
| 상태값(예: 결제 성공 `SUCCESS`)처럼 업무에서 쓰는 값 | 운영자가 따라 할 처리 절차 → **운영 절차서** |

- 근거: 정책은 기획·재무가 승인하는 문서다. 구현 상세가 섞이면 승인자가 읽을 수 없고, 구현이 바뀔 때마다 승인을 다시 받아야 한다.
- 결과로 **고객이 겪는 일**(이용권 소멸, 이용 종료 등)은 정책이다. 그 결과를 **만드는 방법**(작업, 락, 트랜잭션)은 설계다.

### 2. 규칙 ID 체계

- 형식: `{도메인 약어}-{분류}{두 자리 번호}` — 예: `REF-T01`
- 도메인 약어: 영문 3자 대문자. 정책 문서 머리말에 `규칙 ID 약어: {XXX}`로 적고, 같은 저장소 `policies/`의 다른 정책 문서와 겹치지 않게 한다. 예:

  | 약어 | 도메인 |
  |---|---|
  | `REF` | 환불(Refund) |
  | `STL` | 정산(Settlement) |

- 분류

  | 분류 | 의미 | 위반 시 |
  |---|---|---|
  | `T` | 대상 여부(Target) 규칙 — 판정을 진행할 수 있는 상태인지 | 즉시 거절, 이후 평가 중단 |
  | `C` | 가능 조건(Condition) 규칙 — 대상인 건이 요건을 충족하는지 | 모두 평가하고 위반을 전부 기록 |
  | `P` | 파라미터(Parameter) — 규칙이 참조하는 기준값 | — |

- 번호는 **만든 순서**다. 평가 순서나 중요도와 무관하다(그것은 `우선순위` 열이 정한다).
- ID는 영구 식별자다. 폐지한 ID는 **재사용하지 않고**, 번호를 다시 매기지 않는다. 폐지 사실은 변경 이력에 남긴다.
- 근거: ID가 문서·코드·판정 기록·테스트를 잇는 추적 키이기 때문이다. 같은 ID가 시점에 따라 다른 규칙을 가리키면 과거 판정 기록을 해석할 수 없다.

### 3. 표기법

| 표기 | 의미 | 예 |
|---|---|---|
| `[결정 필요 D-xx]` | 결정권자(기획·재무·법무)가 정해야 하는 항목. 선택지는 문서 끝 **미결 항목** 표(§7)에 둔다. 장단점 같은 긴 검토는 검토 메모에 둔다 | `[결정 필요 D-01]` |
| `(예시)` | 실제 정책 문서 안에서, 구조를 보여주려고 임시로 넣은 값. 실제 정책 값이 아니다 | `30% (예시)` |
| `` `식별자` `` | 코드·상태값. 처음 나올 때 한글 설명을 함께 쓴다 | 결제 성공(`SUCCESS`) |

- `D-xx` 번호도 규칙 ID처럼 재사용하지 않는다. 결정되면 본문에 반영하고 미결 항목 표에서 지운 뒤, 변경 이력에 남긴다.

### 4. 용어

- 업계·법령에서 쓰는 표준 용어를 먼저 쓴다. 새 용어를 만들어야 하면 용어 사전에 정의를 남긴다.
- 같은 개념은 문서 전체에서 한 단어로만 부른다(유비쿼터스 언어).

## 템플릿 본문

```markdown
# {도메인} 비즈니스 정책

> 상태: {초안 | 검토 중 | 확정} · 버전: v{x.y} · 최종 수정: {YYYY-MM-DD} · 승인: {승인 부서 / 미정}
> 규칙 ID 약어: {XXX}
> 검토 메모: {링크 (있으면)}
```

**작성 예**

```markdown
# 이용권 환불 비즈니스 정책

> 상태: 확정 · 버전: v1 · 최종 수정: 2026-01-01 · 승인: 기획·재무
> 규칙 ID 약어: REF
> 검토 메모: 이용권_환불_검토메모.md
```

> 작성 가이드: 상태가 "확정"이 아니면 머리말에 `⚠️ 검토용 중간 산출물`이라고 쓴다. 승인 부서가 정해지지 않았으면 "미정"으로 둔다.

### 1. 용어 사전 (필수)

| 용어 | 정의 |
|---|---|
| {용어} | {정의 — 한 문장 + 필요하면 예} |

**작성 예**

| 용어 | 정의 |
|---|---|
| 남은 비율 | 구매한 이용량 중 아직 쓰지 않은 비율(%). 예: 10시간권 중 3시간 남음 → 30%. 환불 가능 조건(REF-C01) 판정과 환불 금액 계산에 쓴다 |
| 환불 완료 | PG가 결제 취소를 확정한 때. 이때 이용권 소멸과 정산의 환불 기록이 함께 일어난다 |

> 작성 가이드
> - 본문에 나오는 판정·금액 관련 용어는 모두 여기 정의한다.
> - 업무 용어와 정의만 쓴다. 용어가 코드에서 어떤 이름인지(모델·필드·enum)는 설계서의 용어–코드 대응표에 둔다. 코드 이름이 바뀌어도 정책 문서는 고치지 않는다.
> - 정의에는 "어디에 쓰는지"까지 적는다.
> - 처리가 끝나는 시점과 중간 상태(완료, 처리 중 등)는 용어로 정의하고, 판정 결과 표의 시점 열에서 그 용어를 쓴다.

### 2. 정책 본문 (필수)

> 작성 가이드: **판정형**(할 수 있는가)과 **계산형**(얼마인가)을 다른 절로 나눈다. 판정 규칙과 금액 규칙은 바뀌는 시점과 결정 주체가 다르기 때문이다.

#### 2-1. {판정 이름} (판정형, 필수)

##### 평가 순서

1. **대상 여부(T) 규칙**을 `우선순위` 순으로 확인한다. 하나라도 어기면 즉시 거절하고 평가를 중단한다.
2. **가능 조건(C) 규칙**은 전부 평가하고, 어긴 규칙을 모두 기록한다.
3. **대표 사유**는 어긴 규칙 중 `우선순위` 숫자가 가장 작은 규칙으로 한다.
4. **판정 결과**는 결정 테이블의 결과 코드로 정하고, 결과별로 일어나는 일은 아래 **판정 결과** 표를 따른다.

##### 결정 테이블

| 우선순위 | 규칙 ID | 구분 | 조건 | 판정 기준 | 결과 코드 | 거절 사유 코드 | 파라미터 | 예외 승인 |
|---|---|---|---|---|---|---|---|---|
| {10} | {XXX-T01} | 대상 여부 | {업무 언어로 쓴 조건} | {무엇을 보고 참/거짓을 정하는지} | `{RESULT_CODE}` | `{REASON_CODE}` | - | 불가 |
| {10} | {XXX-C01} | 가능 조건 | {조건} | {판정 기준} | `{RESULT_CODE}` | `{REASON_CODE}` | {XXX-P01 / -} | {불가 / 가능(§5)} |
| - | - | - | 어긴 규칙 없음 | - | `{RESULT_CODE}` | - | - | - |

**작성 예**

| 우선순위 | 규칙 ID | 구분 | 조건 | 판정 기준 | 결과 코드 | 거절 사유 코드 | 파라미터 | 예외 승인 |
|---|---|---|---|---|---|---|---|---|
| 10 | REF-T01 | 대상 여부 | 결제가 성공 상태가 아님 | 결제 상태가 결제 대기(`PENDING`)·요청 중(`REQUESTED`)·실패(`FAILED`)·취소(`CANCELLED`) 중 하나 | `REJECTED` | `PAYMENT_NOT_COMPLETED` | - | 불가 |
| 10 | REF-C01 | 가능 조건 | 남은 비율이 기준보다 낮음 | 남은 비율(2-2) < REF-P01 | `REJECTED` | `REMAINING_BELOW_THRESHOLD` | REF-P01 | 가능(§5) |
| - | - | - | 어긴 규칙 없음 | - | `AUTO_REFUND` | - | - | - |

> 작성 가이드
> - 이 표는 업무 판정 표준인 **DMN**(Decision Model and Notation) 방식을 따른다. 표는 **결과 코드까지만** 내고, 결과에 따라 일어나는 일은 아래 판정 결과 표에 쓴다. 평가 순서 1~3번은 DMN의 적중 정책에 해당한다(T 규칙 = First, C 규칙 = Collect, 대표 사유 = Priority).
> - 맨 아래 **"어긴 규칙 없음" 행**에는 모든 규칙을 통과했을 때의 결과 코드를 쓴다.
> - **T와 C 구분 기준**: 이미 일어난 사실·상태(결제 미완료, 이미 처리됨, 처리 중)를 확인하면 `T`, 충족 여부를 따지는 요건(기한, 비율, 금액)이면 `C`다.
> - **예외 승인 열**은 `불가` / `가능(§5)` 둘 중 하나로 쓴다. `T` 규칙은 항상 `불가`다. 가능 여부는 이 열에만 두고, 허용 사유·권한자는 §5에 둔다.
> - **조건과 판정 기준을 둘 다 쓴다.** 조건은 사람이 읽는 문장이고, 판정 기준은 시스템이 참/거짓을 정할 수 있는 근거(상태값, 비교식, 기준 시각)다. 판정 기준이 없으면 경계 사례(예: 결제가 성공했다가 취소된 건)가 해석에 맡겨진다.
> - 상태값으로 판정하면 **해당하는 값을 모두 나열**한다. "완료되지 않음"처럼 부정형으로 쓰면 빠지는 값이 생긴다.
> - **우선순위 열만이 기준**이다. 행은 구분별·우선순위 순으로 정렬해 두지만, 행 순서나 ID 번호는 기준이 아니다.
> - 우선순위는 **같은 구분(T끼리, C끼리) 안에서만 비교**한다. `T`를 어기면 평가가 끝나 `C`는 평가하지 않으므로, 두 구분이 서로 비교될 일이 없다. 10 단위로 띄워 매기면(10, 20, 30…) 사이에 규칙을 끼워 넣기 쉽다(예: 15).
> - 기준값은 숫자를 직접 쓰지 않고 파라미터 ID(`XXX-P01`)로 참조한다.
> - 판정 시점(신청 시 / 승인 시 / 실행 직전)이 결과에 영향을 주면 표 아래에 명시한다.
> - 판정 기준에 시각을 쓸 때는 **무엇의 시각인지**(예: 환불 신청 시각) 쓰고 용어 사전에 정의한다. 기한과 비교할 때는 당일을 포함하는지 적는다.
> - 규칙을 폐지하면 행을 지우고, 표 아래와 변경 이력에 폐지 사유를 남긴다.

##### 판정 결과

| 결과 코드 | 판정 결과 | 일어나는 일 | 시점 |
|---|---|---|---|
| `{RESULT_CODE}` | {결과 이름} | {고객의 이용권·결제·이용 상태가 어떻게 되는지} | {언제 일어나는지 — 용어 사전의 시점 용어로} |

**작성 예**

| 결과 코드 | 판정 결과 | 일어나는 일 | 시점 |
|---|---|---|---|
| `REJECTED` | 거절 | 이용권·결제에 변화 없음. 대표 사유의 안내 문구(§4)를 보여준다. 대표 사유가 REF-C01이면 예외 승인을 요청하는 방법(§5)도 안내한다 | 신청 즉시 |
| `AUTO_REFUND` | 자동 환불 | 환불 금액(§2-3)만큼 결제 취소를 요청한다. 취소가 확정되면 이용권이 소멸하고 정산에 환불이 기록된다 | 취소 요청: 신청 즉시 / 소멸·정산: 환불 완료 시 |

> 작성 가이드
> - 결정 테이블의 결과 코드 열에 나오는 코드를 **모두, 빠짐없이** 행으로 둔다. 다른 절(예: §5 예외 승인)에서 생기는 결과는 그 절의 결과 표에 둔다.
> - 같은 결과 코드를 내는 규칙이 여러 개여도 동작은 결과마다 **한 번만** 쓴다. 규칙마다 다른 것은 안내 문구뿐이며, 그것은 §4에 둔다.
> - 고객이 겪는 결과만 쓰고, 그 결과를 만드는 방법(작업, 락, 트랜잭션)은 설계서에 둔다.

| 반올림·절사 | {규칙} |
| 미정 | {항목} — `[결정 필요 D-xx]` |

**작성 예** (2-3. 환불 금액)

| 항목 | 정책 |
|---|---|
| 기준 금액 | 이용권별 실결제액(할인 적용 후 금액) |
| 계산식 | 기준 금액 × 남은 비율(2-2) |
| 상한 / 하한 | 상한은 기준 금액, 하한은 0원 |
| 횟수 | 이용권 1개당 환불 1회 |
| 반올림·절사 | 10원 미만 절사 |
| 미정 | 결제 수수료 공제 여부 — `[결정 필요 D-01]` |

> 작성 가이드: 항목을 비워 두지 말고, 정해지지 않았으면 `미정`과 `D-xx`를 쓴다. "해당 없음"이면 이유를 한 줄 적는다.

### 3. 파라미터 (기준값) (없으면 한 줄)

| 파라미터 ID | 정책 버전 | 적용 대상 | 값 | 시행일 | 근거 |
|---|---|---|---|---|---|
| {XXX-P01} | {v1} | {전체 / 상품 유형} | {값} | {YYYY-MM-DD} | {약관 조항 / 결정 문서} |

**적용 원칙**: {구매 시점 버전 / 판정 시점 버전 — 결정 전이면 `[결정 필요 D-xx]`}

**작성 예**

| 파라미터 ID | 정책 버전 | 적용 대상 | 값 | 시행일 | 근거 |
|---|---|---|---|---|---|
| REF-P01 | v1 | 시간권 | 30% | 2026-01-01 | 이용약관 제12조 |
| REF-P01 | v1 | 정기권 | 50% | 2026-01-01 | 이용약관 제12조 |

**적용 원칙** 작성 예: 구매 시점의 정책 버전을 적용한다.

> 작성 가이드
> - 파라미터로 만드는 것은 **운영 중 값만 바뀔 수 있는 것**(기간, 비율, 금액)이다. 상태 목록처럼 규칙의 뜻을 정하는 것은 파라미터가 아니라 판정 기준에 둔다. 그런 것이 바뀌면 규칙 변경이다.
> - 규칙은 결정 테이블에서 파라미터 ID로만 참조한다. 값은 **적용 원칙으로 버전을 고르고 → 적용 대상으로 행을 고르는** 순서로 찾는다.
> - 정책 버전은 "언제부터", 적용 대상은 "누구에게"다. 대상별 값이 다르면 같은 버전 안에 대상별 행을 둔다(버전 번호로 대상을 나누지 않는다).
> - 값을 바꾸면 행을 고치지 않고 **새 버전 행을 추가**한다. 과거 판정을 재현해야 하기 때문이다.
> - 근거 열은 비우지 않는다. 약관 조항이나 결정 기록을 링크한다.
> - 기준값이 없으면 "현재 판정에 쓰는 기준값은 없다"고 쓰고 표는 생략한다.

### 4. 거절 사유 코드 (필수)

| 거절 사유 코드 | 규칙 ID | 고객 안내 문구 |
|---|---|---|
| `{REASON_CODE}` | {XXX-T01} | {고객에게 보여줄 문장} |
| `{REASON_CODE}` | {XXX-C01} | {문장, 치환값은 `{name}`} |

**작성 예**

| 거절 사유 코드 | 규칙 ID | 고객 안내 문구 |
|---|---|---|
| `PAYMENT_NOT_COMPLETED` | REF-T01 | 결제가 완료되지 않은 주문입니다. |
| `REMAINING_BELOW_THRESHOLD` | REF-C01 | 남은 이용량이 {threshold}% 미만이라 환불할 수 없습니다. (현재 {actual}%) |

> 작성 가이드
> - 규칙 1개에 사유 코드 1개를 둔다. 코드는 `UPPER_SNAKE_CASE`로 쓰고, 바뀌지 않는다. 문구는 코드와 별개로 바꿀 수 있다.
> - 문구의 치환값(`{threshold}`, `{actual}` 등)은 판정할 때 기록한 값에서 가져온다고 적는다. 표시 시점에 다시 계산하면 문구와 판정이 어긋난다.

### 5. 예외 승인 (없으면 한 줄)

판정(§2-1)이 거절로 끝나고 고객에게 안내(§4)된 뒤에, {예외 승인을 시작하는 계기}로 시작하는 별도 절차다. 위반한 규칙이 모두 결정 테이블에서 예외 승인 `가능(§5)`이고 아래 허용 사유에 해당하면, 권한자가 이 건에 한해 거절을 뒤집을 수 있다. 판정 기록은 바꾸지 않고 승인 기록을 따로 남긴다.

**작성 예** (시작 계기): 고객이 이의를 제기하며 증빙을 내거나, 매장 점주가 직접 판단한 경우.

| 규칙 ID | 허용 사유 | 권한자 | 승인 시 필수 기록 |
|---|---|---|---|
| {XXX-C01} | {예외를 허용하는 구체적인 사유} | {승인 권한자} | {남길 항목} |

**작성 예**

| 규칙 ID | 허용 사유 | 권한자 | 승인 시 필수 기록 |
|---|---|---|---|
| REF-C01 | 질병·입원 등으로 이용할 수 없었음 | 매장 점주 | 승인자, 승인 시각, 승인 사유, 증빙(진단서 등) |

##### 예외 승인 결과

| 결과 코드 | 판정 결과 | 일어나는 일 | 시점 |
|---|---|---|---|
| `{RESULT_CODE}` | {결과 이름} | {고객의 이용권·결제·이용 상태가 어떻게 되는지} | {언제 일어나는지} |

**작성 예**

| 결과 코드 | 판정 결과 | 일어나는 일 | 시점 |
|---|---|---|---|
| `EXCEPTION_REFUND` | 예외 환불 | 환불 금액(§2-3)만큼 결제 취소를 요청한다. 취소가 확정되면 이용권이 소멸하고 정산에 환불이 기록된다 | 취소 요청: 승인 즉시 / 소멸·정산: 환불 완료 시 |

> 작성 가이드
> - 결정 테이블에서 예외 승인이 `가능(§5)`인 규칙만 허용 사유 표에 둔다.
> - 허용 사유는 판단 기준이 되도록 구체적으로 쓴다(예: "고객 사정"이 아니라 "질병·입원").
> - 예외 승인은 규칙을 바꾸는 것이 아니라 **한 건의 결과**를 바꾸는 것이다. 같은 사유의 예외가 반복되면 규칙이나 기준값을 고친다.
> - `T` 규칙은 결제 여부나 이미 처리됐는지 같은 사실을 확인하므로 판단으로 뒤집을 수 없다. 그래서 이 표에 두지 않는다.
> - 예외 승인으로 생기는 결과와 그때 일어나는 일은 **이 절의 결과 표에서 완결**한다. §2-1 판정 결과 표에 섞지 않는다.
> - 예외 승인이 가능한 규칙이 없으면 "예외 승인이 가능한 규칙은 없다"고 쓰고 표는 생략한다.

## 작성 예 따라 읽기

작성 예("이용권 환불 정책 v1")로 판정 하나를 처음부터 끝까지 따라간다. 정책 문서를 읽거나, 고객에게 거절 이유를 설명할 때 이 순서로 각 절을 본다.

### 기본 흐름

**전제**: 고객이 2026-03-01에 30일 정기권을 사고(결제 성공), 12일이 남은 상태에서 환불을 신청했다.

| 단계 | 질문 | 볼 곳 | 이 사례의 답 |
|---|---|---|---|
| 1 | 환불 대상인가? | §2-1 › 결정 테이블 › REF-T01 행의 판정 기준 | 결제 상태 `SUCCESS` → 통과 |
| 2 | 요건을 충족하는가? | §2-1 › 결정 테이블 › REF-C01 행의 판정 기준 | 남은 비율 < REF-P01인지 확인 → 2a, 2b로 값을 구한다 |
| 2a | └ 남은 비율은? | §1 용어 사전 › "남은 비율" → §2-2 › "정기권" 행 | 12 ÷ 30 × 100 = 40% |
| 2b | └ REF-P01은? | §3 파라미터 › 적용 원칙(버전) → "정기권" 행(값) | 구매 시점 버전 v1 → 50% |
| 2c | └ 비교 | §2-1 › 결정 테이블 › REF-C01 행의 판정 기준 | 40 < 50 → 위반 |
| 3 | 대표 사유는? | §2-1 › 평가 순서 3번 → 결정 테이블 › REF-C01 행의 거절 사유 코드 | `REMAINING_BELOW_THRESHOLD` |
| 4 | 판정 결과와 일어나는 일은? | §2-1 › 결정 테이블 › REF-C01 행의 결과 코드 → 판정 결과 표 › `REJECTED` 행 | 거절. 이용권·결제에 변화 없음 |
| 5 | 고객에게 뭐라고 안내하는가? | §4 › `REMAINING_BELOW_THRESHOLD` 행의 고객 안내 문구 | "남은 이용량이 50% 미만이라 환불할 수 없습니다. (현재 40%)" + 예외 승인 요청 방법 안내 → **흐름 종료** |

### 갈래 A: 예외 승인

**전제**: 기본 흐름 5단계 이후, 고객이 입원으로 이용하지 못했다며 증빙을 냈다.

| 단계 | 질문 | 볼 곳 | 이 사례의 답 |
|---|---|---|---|
| A1 | 예외 승인할 수 있는가? | §2-1 › 결정 테이블 › REF-C01 행의 예외 승인 → §5 › REF-C01 행의 허용 사유 | 위반은 REF-C01 하나이고 `가능(§5)`, 입원은 허용 사유 "질병·입원"에 해당 → 매장 점주가 승인하고 승인자·시각·사유·진단서를 기록 |
| A2 | 승인 결과와 일어나는 일은? | §5 › 예외 승인 결과 › `EXCEPTION_REFUND` 행 | 결제 취소를 요청하고, 환불 완료 시 이용권 소멸·정산 기록 |
| A3 | 환불 금액은? | §2-3 › 계산식, 반올림·절사 | 실결제액 × 40%, 10원 미만 절사 |

### 갈래 B: 요건 충족

**전제**: 기본 흐름과 같고, 남은 일수만 18일이다.

| 단계 | 질문 | 볼 곳 | 이 사례의 답 |
|---|---|---|---|
| B1 | 요건을 충족하는가? | 기본 흐름 2a~2c와 같음 | 18 ÷ 30 × 100 = 60%, 60 < 50 거짓 → 통과 |
| B2 | 판정 결과와 일어나는 일은? | §2-1 › 결정 테이블 › "어긴 규칙 없음" 행 → 판정 결과 표 › `AUTO_REFUND` 행 | 자동 환불. 결제 취소를 요청하고, 환불 완료 시 이용권 소멸·정산 기록 |
| B3 | 환불 금액은? | §2-3 › 계산식, 반올림·절사 | 실결제액 × 60%, 10원 미만 절사 |

### 참고

- 규칙이 언제, 왜 생겼는지는 §6 변경 이력 › v1 행에서 확인한다(2026-01-01, 이용약관 제12조 제정).
- 하위 단계(2a~2c)는 규칙을 판정하는 데 필요한 값을 구하는 과정이다. 번호에 "2-1" 대신 "2a"를 쓴 것은 절 번호와 구분하기 위해서다.
