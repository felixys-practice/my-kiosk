# 환불 비즈니스 정책

> 검토용 정책 문서 · 버전 v0.4 · 최종 수정 2026-10-27
>
> 이용 종료와 환불금 지급을 분리하는 사용자 결정을 반영했다. 실제 구현·PG·은행 연동 검증은 별도다.
> 기준: [002 기능 명세](../../specs/002-refund-completion/spec.md), [계획](../../specs/002-refund-completion/plan.md), [데이터 모델](../../specs/002-refund-completion/data-model.md), [API 계약](../../specs/002-refund-completion/contracts/rest-api.md).
> 기존 architecture 환불 문서는 과거 설계 이력이며 v0.4 구현 기준으로 사용하지 않는다.

### 1. 용어 사전

| 용어 | 정의 |
|---|---|
| 이용권 | 주문 상품 1개에 대응하는 고객의 시간권 또는 정기권 |
| 시간권 | 구매한 시간만큼 이용하며 소진 기한 안에 사용해야 하는 이용권 |
| 정기권 | 활성화한 날부터 구매 기간 동안 이용하는 이용권. 활성화 전에는 활성화 기한이 적용됨 |
| 실결제액 | 해당 이용권에 실제 낸 금액, 정상 환불 금액의 상한 |
| 확정된 환불 금액 | 환불 확정 시 고객에게 돌려주기로 정한 금액(Refund.amount). PG 지연·실패나 실제 지급액과 달라도 바꾸지 않으며 실제 PG 취소액·실제 지급 합계·미지급액과 구분함 |
| 거절 확정 | PG가 해당 취소 요청을 거절했고 취소가 실행되지 않았으며 앞으로도 진행되지 않는다고 확정 응답한 경우. 오류 문자열만으로 실행 여부가 불명확하면 해당하지 않음 |
| PG 취소 요청 | 서버가 PG에 확정된 환불 금액만큼 결제를 취소해 달라고 보내는 요청. 서버가 PG 취소 요청 식별자를 붙여 결과를 기록함 |
| 새 식별자를 발급한 PG 취소 요청 | 실패한 요청을 대신해 새 PG 취소 요청 식별자로 보내는 PG 취소 요청. 기존 환불 건·금액과 이전 실패 기록은 유지함 |
| 미사용·사용 이력 | 2-2의 순서로 판단. 이용 중은 사용 이력에 포함 |
| 신청 시각 | 고객·점주가 환불 신청을 시작한 시각. 이용 기한 판정 기준 |
| 신청 거절 | 검증·동의 확인 실패. 새 환불 기록과 이용 종료를 만들지 않음 |
| 환불 확정 | 검증·동의를 마쳐 이용 종료와 금액을 확정한 업무 결정. PG 결제 취소 실패로 철회하지 않음 |
| 환불금 지급 | 확정된 환불 금액을 고객에게 돌려주는 것. PG 취소 완료 또는 증빙으로 확인한 PG 외 실제 전달을 포함 |
| 별도 환불금 지급 | 운영자가 PG 외 수단으로 환불금을 실제 전달하고 예약·증빙·결과를 기록하는 절차. 실제 송금 실행은 시스템 범위 밖 |
| 환불금 지급 처리 중 | 확정된 환불 금액의 PG 요청·재조회·재전송 중. 환불금 지급 완료가 아님 |
| PG 취소 결과 확인 실패 | PG 조회 자체가 연속 실패해 실제 결과를 모름. 다른 환불금 지급을 시작할 수 없음 |
| PG 취소 요청 실패 | PG 거절·확실한 미전송·미접수 재전송 한도 초과 등 한 PG 취소 요청의 결과 |
| 환불금 지급 조치 필요 | 확정된 환불 금액의 미지급·금액 불일치를 운영자가 해결해야 하는 상태 |
| 환불금 지급 완료 | 확정된 환불 금액의 실제 지급 확인과 필요한 검토가 끝난 상태. 고객 은행 명세 반영 시점과는 구분 |
| 별도 환불금 지급 | PG 외 실제 지급을 운영자가 예약하고 증빙을 기록하는 절차. 시스템의 송금 실행은 아님 |

### 2. 정책 본문

#### 2-1. 환불 판정

대상 여부 규칙을 우선순위대로 확인하고 하나라도 어기면 거절한다. 모두 통과하면 가능 조건을 모두 평가한다. 대표 사유는 우선순위 숫자가 작은 위반이며, 가능 조건 거절은 매장 요청을 안내한다.

| 우선순위 | 규칙 ID | 구분 | 조건·판정 기준 | 결과 | 오류 코드 | 매장 예외 |
|---|---|---|---|---|---|---|
| 10 | REF-T06 | 대상 여부 | 본인/소유 매장 범위에서 이용권을 찾을 수 없음 | REJECTED | TICKET_NOT_FOUND | 불가 |
| 20 | REF-T02 | 대상 여부 | 이용권 주문의 결제가 SUCCESS가 아님 | REJECTED | PAYMENT_NOT_COMPLETED | 불가 |
| 30 | REF-T03 | 대상 여부 | 같은 이용권의 확정 환불이 환불금 지급 완료됨 | REJECTED | ALREADY_REFUNDED | 불가 |
| 40 | REF-T04 | 대상 여부 | 환불 없는 강제 폐기, 현재 적용 보류 | REJECTED | TICKET_REVOKED | 불가 |
| 50 | REF-T05 | 대상 여부 | 같은 이용권에 확정됐지만 지급이 끝나지 않은 환불 존재. 시도 실패·조치 필요·별도 환불금 지급 확인 중 포함 | REJECTED | REFUND_IN_PROGRESS | 불가 |
| 10 | REF-C01 | 가능 조건 | 사용 이력 있음 | REJECTED | USED_TICKET | 가능 |
| 20 | REF-C03 | 가능 조건 | 미사용이며 이용 기한이 신청 시각보다 앞섬 | REJECTED | EXPIRED_TICKET | 가능 |
| - | - | 모두 통과 | 고객 또는 점주가 미사용 전액 환불을 확정 | AUTO_REFUND | - | - |

- 소멸 상태만으로 환불금 지급 완료를 판단하지 않는다. 환불금 지급 실패 후에도 이용권은 종료 상태이므로 해당 환불의 환불금 지급 상태를 확인한다.
- REF-T04는 환불 없이 이용권을 폐기하는 기능이 생길 때 적용한다. 환불 확정 후 아직 미지급인 이용권은 REF-T04가 아니라 REF-T05다.
- 신청 시각과 기한이 같으면 기한 안이다. 고객은 본인 범위, 점주는 현재 소유 매장 범위에서만 찾고 범위 밖의 존재를 드러내지 않는다.

| 판정 | 결과와 시점 |
|---|---|
| REJECTED | 신청 시 오류 응답. 이용권·세션·좌석·새 환불·환불금 지급 기록에 변화 없음 |
| AUTO_REFUND | 종료와 전액 금액의 안내·동의 후 이용권 소멸·좌석 해제·환불을 함께 확정. 이후 PG 결제 취소 시작 |
| STORE_REFUND | 점주가 조건에 맞는 금액·사유를 입력하고 동의를 확인한 뒤 같은 종료·확정 처리. 이용 중이면 퇴실 동의도 필수 |

#### 2-2. 미사용 판정

| 순서 | 조건 | 판정 |
|---|---|---|
| 1 | 지금 이용 중 | 사용 이력 있음 |
| 2 | 정기권·활성화 전 | 미사용 |
| 3 | 시간권·남은 시간=구매 시간 | 미사용 |
| 4 | 그 외 | 사용 이력 있음 |

#### 2-3. 금액과 횟수

| 항목 | 정책 |
|---|---|
| AUTO_REFUND | 실결제액 전액. 점주 대행도 전액 |
| STORE_REFUND | 점주 입력액. 0원부터 실결제액까지, 사용/기한 초과는 사유 필수 |
| 횟수 | 이용권당 환불 확정 1회. PG 취소 재요청은 같은 환불 건에서 수행 |
| 확정 후 금액 | 확정된 환불 금액은 불변. PG 실제액은 따로 보존하고 부족액·초과액을 표시 |
| 0원 | PG 결제 취소 없이 이용 종료·좌석 해제·환불 확정·환불금 지급 완료·원장 0원을 함께 기록 |
| 지급 일부 확인 | 실제액만 합산하고 부족액만 별도 환불금 지급. 이용권을 계속 쓰게 하는 부분 환불 상품은 아님 |

미사용 이용권의 전액 환불은 이용 기한 안인 경우에만 적용한다. 기한이 지난 미사용 이용권은 고객 자동 환불 대상이 아니며, 점주가 0원부터 실결제액까지 금액과 사유를 정한다. 정기권은 활성화 기한, 시간권은 소진 기한을 기준으로 판정한다(2026-10-26 기존 규칙 유지 확정).

#### 2-4. 이용 종료와 고객 안내

1. 환불 확정 시점부터 이용 권리는 끝난다. 필요한 퇴실·시간권 사용량 차감·이용권 소멸·고정석 해제·환불 기록을 함께 저장한다.
2. 종료 동의에는 금액과 PG 지연·실패에도 이용권이 자동 복구되지 않음을 포함한다. 이용 중이면 퇴실 동의도 받는다. 점주에게 별도 퇴실 API 실행을 요구하지 않는다.
3. 검증이나 동의 확인에 실패하면 퇴실·종료·좌석 해제를 하지 않는다.
4. 정기권의 PG 대기 기간을 정지/연장하지 않는다. 시간권의 사용량과 기한도 복구하지 않는다. 기존 정지 중인 이용권은 재개 없이 정지 기록을 닫는다.
5. 종료된 이용권은 환불금 지급 성공·실패·미확정과 관계없이 입실·재개·좌석 타입 변경을 할 수 없다. 고정석을 다시 판매할 수 있고 재배정·가격 차이를 환불 실패 복구에 넣지 않는다.
6. 응답과 내역에 이용 종료 완료·확정된 환불 금액·환불금 지급 상태·미지급액을 나누어 보여준다. PG 전송 실패는 환불 신청 거절로 안내하지 않는다.

#### 2-5. 지급과 미지급 후속 처리

- PG 취소 완료는 실제 취소액으로 PG 취소 요청과 원장을 함께 기록한다. 확정된 환불 금액과 일치하고 다른 확인 사항이 없으면 환불금 지급 완료다.
- 전송 전 실패·PG 거절은 시도 실패와 환불금 지급 조치 필요다. 확정된 환불 금액은 유지한다. 운영자는 원인 조치 후 직접 재시도하거나 환불금을 별도로 지급하고 점주·운영자는 아래 개별 확인 조건으로도 다시 보낼 수 있다.
- 응답이 없으면 PG에 먼저 조회한다. 결과가 불명확한 동안 새 식별자를 발급한 PG 취소 요청·별도 환불금 지급은 금지한다.
- 백그라운드 자동 작업은 PG 미접수가 확실히 확인된 때만 고객·매장·시스템 경로 모두 같은 시도·같은 금액으로 한도 내 재전송한다. 한도를 모두 소진한 전송도 PG 미접수가 확인돼야 자동 PG 취소 요청을 실패로 끝내고 자동 재전송에서 제외한다. 확정 환불은 운영자 지급 처리 대상으로 계속 남는다. PG 처리 중·조회 장애이면 한도 소진 뒤에도 조회를 이어간다.
- 조회 장애는 간격을 늘려 확인하고 연속 오류 한도에 도달하면 PG 취소 결과 확인 실패로 알린다. 이후 전체에서 가장 오래된 1건의 복구 조회, 정상 응답 뒤 나눠 조회한다. 운영자도 같은 방식으로 바로 조회를 재개할 수 있다.
- 해당 매장 점주와 운영자는 미확정 PG 취소 요청 또는 최근 시도가 이미 RETRY_EXHAUSTED·SEND_FAILED·PG_REJECTED로 FAILED인 환불 한 건을 개별 확인할 수 있다. 다른 유효 담당·최근 조회가 있으면 중복 호출하지 않는다. 미확정 시도의 확실한 미접수는 기존 ID·금액으로 재전송한다. 이미 FAILED인 세 사유는 미접수 또는 거절 확정 후 실제 지급액 0·다른 미확정 지급 없음·PG 방식·활성 예약 없음·유효한 자기 담당 토큰을 확인하고 이전 실패를 보존한 새 ID의 요청을 즉시 보낸다. 별도 버튼·사유 입력은 요구하지 않는다. 조회 오류이면 실패 이력을 유지하고 보내지 않으며, 실패 확정 건의 처리 중·취소 성공 등 모순 결과는 PG_RESULT_CONFLICT·운영자 알림과 추가 지급 차단으로 처리한다. 미확정 요청의 조회에서 새로 확인한 거절은 실패·조치 필요만 기록한다. 자동 재전송 한도는 백그라운드 작업에만 적용한다. 다른 환불을 일괄 조회하지 않고 지급 완료·0원·활성 별도 예약·금액 불일치 검토·다른 확정 실패·MANUAL 방식은 저장 상태만 반환한다.
- 확정 실패의 직접 재시도(payout-retries)는 운영자(MANAGER)만 실행한다. 고객·점주는 사유 입력 여부와 관계없이 REFUND_FORBIDDEN(403)으로 거부한다. 운영자는 원인 조치 후 실제 지급액 0·모든 PG 결과 확정·활성 예약 없음 등 재시도 조건을 확인하고 사유·요청 키를 입력한다. 새 PG 취소 요청 식별자로 확정된 환불 금액을 보내며 이전 실패 기록을 보존한다. 같은 키·같은 내용은 현재 상태와 관계없이 최초 응답을 반환한다. 새 요청의 지급 완료 등 재처리 불가 상태는 REFUND_PAYOUT_NOT_ACTIONABLE(409), 미확정 지급·예약은 REFUND_PAYOUT_UNRESOLVED(409), 미지급액이 남은 일부 지급은 REFUND_PARTIAL_PAYOUT_REQUIRES_MANUAL(409)로 거절한다. 새 요청의 자동 횟수는 0부터 시작하고 이후 자동 작업은 미접수·한도 조건을 적용한다. 사람의 개별 확인이나 운영자 직접 실행 없이 다음 요청 기록을 추가하지 않는다.
- 지급 미완료 건은 삭제·완료 숨김 처리하지 않고 담당자가 조회·처리할 수 있게 남긴다. 시간 초과로 이용권을 복구하거나 새 지급을 허용하지 않는다.
- PG 실제액이 부족하면 부족액만 환불금을 별도로 지급한다. 부족액 실제 환불금 지급 증빙을 확정할 때 검토도 함께 완료해 전체 지급을 마친다. 초과 지급이면 추가 환불금 지급을 막고 운영자가 증빙·사유로 검토한 뒤 환불금 지급 완료로 정리한다. 확정된 환불 금액·실제액·원장은 덮어쓰지 않는다.

#### 2-6. 별도 환불금 지급·원장

- MANAGER가 모든 PG 결과 확정·미지급액·다른 환불금 지급 없음 확인 후 미지급액과 같은 지급을 예약한다. 예약과 동시에 PG 재시도·다른 별도 환불금 지급을 막는다.
- 실제 송금은 외부에서 한다. 운영자가 실제 지급 거래 ID·시각·금액·증빙을 확인해 지급과 원장을 함께 기록한다. 예약만으로 환불금 지급 완료 처리하지 않는다.
- 환불금 지급 여부를 모르면 예약을 유지하고 알린다. 확실한 미지급 증빙과 사유가 있어야 예약을 실패(FAILED)로 종료할 수 있으며 단순 시간 경과는 해제 근거가 아니다. 실패 종료 후 MANUAL에서 PG 지급으로 되돌릴 때는 운영자의 payout-retries로만 재개한다.
- 같은 지급·증빙 거래 ID를 중복 반영하지 않는다. PG 실제액과 부족액 별도 환불금 지급이 있으면 각각 실제 금액의 원장을 1건씩 기록한다. 실패·예약만으로 원장은 만들지 않는다.

### 3. 파라미터

결과 대기·조회 간격·연속 오류 한도·장애 복구 조회 간격·재전송 한도·별도 환불금 지급 확인 지연 알림 기준은 운영 설정이다. 기본값·검증 규칙은 [API 계약](../../specs/002-refund-completion/contracts/rest-api.md)에 둔다. 담당 기한과 실제 환불금 지급 결과는 다르며, 기한이 지나도 결과 불명 상태를 풀지 않는다.

### 5. 매장 환불·운영 권한·알림

고객이 먼저 자동 환불에서 거절당할 필요 없이 점주에게 요청할 수 있다. 점주는 현재 소유 매장 이용권만 처리하며 소진·만료·정지 이용권도 판단할 수 있다. 사용/기한 초과는 금액·사유 필수, 미사용 기한 안이면 전액·사유 선택이다. 점주·시각·금액·사유·동의를 기록한다.

고객지원 계정(MANAGER)은 새 매장 환불 금액을 결정하지 않는다. 기존 환불의 조회·PG 재확인·확정 실패 뒤 PG 취소 재요청·별도 환불금 지급 예약/증빙·금액 불일치 검토를 할 수 있다. PG 결과를 추측해 성공 처리하거나 확정된 환불 금액을 덮어쓸 수는 없다.

고객 환불 환불금 지급 실패는 고객·현재 매장 점주·운영자에게, 매장 환불은 점주·운영자에게, 시스템 취소는 운영자에게 알린다. PG 취소 결과 확인 실패·금액 불일치·별도 환불금 지급 장기 미확인도 운영자 알림 대상이다. 시스템 안 알림·거래 로그를 남기고 읽음은 수신자별로 관리한다.
