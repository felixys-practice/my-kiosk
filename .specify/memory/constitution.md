# my-kiosk 헌법

## 핵심 원칙

### I. 계층 구조

모든 도메인은 Controller → Service → Repository 3계층을 MUST 따른다.

- Controller는 요청·응답 처리만 담당한다.
- Service는 업무 로직을 담당한다.
- Repository는 데이터 접근(Prisma 쿼리)을 담당한다.

**근거**: 계층별 책임을 분리해야 변경 범위를 한 계층으로 좁히고 계층별로 테스트할 수 있다.

### II. 입력 검증

외부 입력을 받는 모든 DTO는 `class-validator`로 MUST 검증한다.

**근거**: 잘못된 입력을 진입 지점에서 차단해야 Service 계층이 검증된 값만 다룬다.

### III. 테스트

- 새 기능은 단위 테스트와 E2E 테스트를 MUST 함께 작성한다.
- 테스트는 구현보다 MUST 먼저 작성한다.
- 구현 전에 테스트를 실행해 실패하는 것을 MUST 확인한다.
- 구현 후 테스트를 통과시키기 위해 테스트의 기대값을 MUST NOT 바꾼다.
  기대값 변경이 필요하면 사용자 확인을 MUST 받는다.

**근거**: 단위 테스트는 로직의 정확성을, E2E 테스트는 계층을 거친 실제 동작을 검증한다.
테스트를 먼저 작성하고 실패를 확인해야 테스트가 구현이 아니라 요구사항을 기준으로 작성되며,
구현에 맞춰 테스트를 고치는 일을 막을 수 있다.

### IV. 운영 수준 코드

모든 코드는 운영 환경에서 사용할 수 있는 수준으로 작성한다. 축약·생략이 필요하면
구현 전에 이유를 설명하고 사용자 확인을 MUST 받는다.

**근거**: 본 프로젝트는 실무 수준의 구현을 학습하는 것이 목적이므로, 임의로 축약하면 그 목적이 훼손된다.

### V. 단순성

요청된 범위만 MUST 구현한다. 요청되지 않은 기능·추상화·설정은 추가하지 않는다.

**근거**: 범위를 넘는 구현은 검토 부담과 유지보수 비용을 늘린다.

## 기술 제약

- 프레임워크: NestJS
- ORM: Prisma
- 데이터베이스: PostgreSQL
- 캐시·큐 저장소: Redis

위 기술 스택을 벗어나는 도입은 사용자 확인을 MUST 받는다.

## 개발 흐름

- 모든 작업은 기능 브랜치에서 MUST 진행한다.
- 커밋 메시지는 한글로 MUST 작성한다.

## 거버넌스

- 본 헌법은 다른 개발 관행보다 우선한다.
- 개정은 변경 내용과 사유를 기록하고 사용자 승인을 받은 뒤 반영한다.
- 버전은 유의적 버전(Semantic Versioning)을 따른다.
  - MAJOR: 원칙 삭제 또는 호환되지 않는 재정의
  - MINOR: 원칙·섹션 추가 또는 지침의 실질적 확장
  - PATCH: 문구 명확화, 오탈자 수정
- `/speckit-plan`의 Constitution Check(헌법 준수 점검)에서 위 원칙 준수 여부를 확인한다.
