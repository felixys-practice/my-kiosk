# my-kiosk 헌법

## 핵심 원칙

### I. 계층 구조

모든 도메인은 Controller → Service → Repository 3계층을 MUST 따른다.

- Controller는 요청·응답 처리만 담당한다.
- Service는 업무 로직을 담당한다.
- Repository는 데이터 접근(Prisma 쿼리)을 담당한다.

**근거**: 계층별 책임을 분리해야 변경 범위를 한 계층으로 좁히고 계층별로 테스트할 수 있다.

### II. 입력 검증

외부 입력을 받는 모든 DTO는 `class-validator`로 MUST 검증한다.

**근거**: 잘못된 입력을 진입 지점에서 차단해야 Service 계층이 검증된 값만 다룬다.

### III. 테스트

- 새 기능은 단위 테스트와 E2E 테스트를 MUST 함께 작성한다. spec.md의 인수 시나리오마다
  HTTP API를 직접 호출하는 E2E 테스트가 MUST 1개 이상 있어야 한다.
- 테스트는 구현보다 MUST 먼저 작성한다.
- 구현 전에 테스트를 실행해 실패하는 것을 MUST 확인한다.
- 테스트를 통과시키려고 기대값 변경, assertion(단언: 결과를 검증하는 `expect` 문) 완화,
  skip(건너뛰기: `it.skip` 등), 삭제, 실행 대상 필터링을 MUST NOT 한다.
  테스트와 코드가 어긋나면 spec.md를 기준으로 판단하고, 테스트를 바꿔야 하면 사용자 확인을 MUST 받는다.
- TDD 사이클의 단위는 동작 하나(테스트 하나)다. 테스트 작성 → 실패 확인 → 최소 구현 →
  전체 테스트 통과 확인 → refactoring(리팩터링: 동작은 그대로 두고 코드 구조만 개선) 필요 여부 확인
  순서를 테스트 하나마다 MUST 거친다. refactoring이 필요하면 이 단계에서 한다.
- 최소 구현은 다음 동작의 조건을 미리 넣지 않는 것이다. 테스트의 기대값을 상수로
  돌려주기만 하는 구현(Fake It: 가짜 구현)은 MUST NOT 커밋한다.
- refactoring은 전체 테스트가 통과한 상태에서만 한다. 테스트를 바꿔야 한다면 refactoring이
  아니라 새 동작이다.
- 실패 확인에서는 테스트가 노리는 이유로 실패하는지 MUST 확인한다. 메서드·필드가 없어
  생기는 오류는 노리는 이유가 아니므로, 빈 구현으로 해당 오류를 넘긴 뒤 다시 실행해 확인한다.
- 실패 확인의 실행 명령과 실제 실패 출력은 `specs/<기능>/tdd/cycle-log.md`에 MUST 기록한다.
  기록은 덧붙이기만 하고 지난 기록은 고치지 않는다.
- 동작 변경과 refactoring은 MUST 다른 커밋으로 나눈다.
- 테스트가 잘못된 구현을 잡아내는지 MUST 확인한다. mutation testing(뮤테이션 테스트: 도구가
  코드를 자동으로 조금씩 바꿔 테스트가 실패하는지 보는 방법) 도구가 있으면 바뀐 파일에 적용하고,
  없으면 주요 동작의 구현을 일부러 깨뜨려 테스트가 실패하는지 확인한다(deliberate mutant: 의도적 변형).
- 여러 테스트를 한꺼번에 작성한 뒤 한꺼번에 실패를 확인하는 방식은 MUST NOT 사용한다.

**근거**: 단위 테스트는 로직의 정확성을, E2E 테스트는 계층을 거친 실제 동작을 검증한다.
테스트를 먼저 작성하고 실패를 확인해야 테스트가 구현이 아니라 요구사항을 기준으로 작성되며,
구현에 맞춰 테스트를 고치는 일을 막을 수 있다. 사이클을 동작 하나 단위로 돌리고 실패 이유까지
확인해야 각 테스트가 실제로 해당 동작을 검증하는지 보장되며, 엉뚱한 이유(정의 누락 등)로
실패하던 테스트가 구현 후 통과해 검증 없이 넘어가는 일을 막을 수 있다.
실패 출력을 별도 기록으로 남기고 git 이력과 대조해야, 테스트를 먼저 작성했다는 사실을 사후에 확인할 수 있다.

### IV. 운영 수준 코드

모든 코드는 운영 환경에서 사용할 수 있는 수준으로 작성한다. 축약·생략이 필요하면
구현 전에 이유를 설명하고 사용자 확인을 MUST 받는다.

**근거**: 본 프로젝트는 실무 수준의 구현을 학습하는 것이 목적이므로, 임의로 축약하면 그 목적이 훼손된다.

### V. 단순성

요청된 범위만 MUST 구현한다. 요청되지 않은 기능·추상화·설정은 추가하지 않는다.

**근거**: 범위를 넘는 구현은 검토 부담과 유지보수 비용을 늘린다.

### VI. 오류 응답

- 요청을 거부하는 응답은 클라이언트의 대응(이용자 안내·다음 행동)이 다른 거부 사유마다 서로 다른
  오류 코드(`error.code`)를 MUST 가진다. 같은 HTTP 상태 코드 안에서도 대응이 다르면 코드를 구분하고,
  대응이 같은 사유는 코드를 공유할 수 있다.
- 기능의 API 계약(contracts)에 거부 상황, HTTP 상태 코드, 오류 코드의 대응을 MUST 명시한다.
- 거부 동작을 검증하는 테스트는 상태 코드와 함께 오류 코드를 MUST 검증한다.
  안내 문구(`error.message`)는 표시용이므로 테스트의 검증 대상이 아니다.
- DTO 형식 검증(`ValidationPipe`) 실패는 공통 코드를 쓰며, 위 구분 대상에서 제외한다.

**근거**: 클라이언트는 오류 코드로 거부 사유를 구분해 이용자에게 안내한다. 문구는 표시용이라
자주 바뀌므로 테스트 기준으로 삼으면 테스트가 쉽게 깨지고, 코드가 구분되지 않으면
사유가 다른 거부를 클라이언트가 구별할 수 없다.

## 기술 제약

- 프레임워크: NestJS
- ORM: Prisma
- 데이터베이스: PostgreSQL
- 캐시·큐 저장소: Redis

위 기술 스택을 벗어나는 도입은 사용자 확인을 MUST 받는다.

## 개발 흐름

- 모든 작업은 기능 브랜치에서 MUST 진행한다.
- 커밋 메시지는 한글로 MUST 작성한다.

## 거버넌스

- 본 헌법은 다른 개발 관행보다 우선한다.
- 개정은 변경 내용과 사유를 기록하고 사용자 승인을 받은 뒤 반영한다.
- 버전은 유의적 버전(Semantic Versioning)을 따른다.
  - MAJOR: 원칙 삭제 또는 호환되지 않는 재정의
  - MINOR: 원칙·섹션 추가 또는 지침의 실질적 확장
  - PATCH: 문구 명확화, 오탈자 수정
- `/speckit-plan`의 Constitution Check(헌법 준수 점검)에서 위 원칙 준수 여부를 확인한다.

### 경과 규정

- v1.2.0 개정(2026-10-22) 이전에 완료된 task는 개정된 원칙 III에 맞춰 MUST NOT 다시 수행한다.
  완료 상태와 원래 설명을 그대로 두고, tasks.md에 이 규정의 적용 대상임을 표시한다.
- 개정 이전에 작성된 테스트도 이 규정에 따라 실패 이유를 소급해 확인하지 않는다.
  해당 테스트가 이후 동작의 사이클에서 다시 실패 확인 대상이 되면 그때 원칙 III을 따른다.
- v1.5.0에서 추가된 규칙은 002 이후 기능부터 적용하고, 001-seat-type에는 소급하지 않는다.

**근거**: 개정 이전 규칙으로 정상 완료한 작업을 새 규칙으로 다시 수행하면, 이미 통과한
구현을 되돌려야 하는 등 비용이 크다. 규칙은 개정 시점 이후의 작업부터 적용한다.
